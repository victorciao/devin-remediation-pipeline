## P-6 — GitHub's issue search **does** index HTML comments in issue bodies, with a short index lag

Method: created `victorciao/devin-remediation-pipeline#2` with
`<!-- devin-remediation-id: probe-marker-1788118425 -->` as the first line of the body
(`201`, `created_at=2026-08-30T19:33:45Z`), then polled `GET /search/issues` for four query shapes
until each returned the issue. Issue closed afterwards.

| query shape | result |
|---|---|
| `repo:… "<!-- devin-remediation-id: … -->"` (full marker, quoted) | found |
| `repo:… "devin-remediation-id: <id>"` (quoted, no comment syntax) | found |
| `repo:… <id>` (bare id) | found |
| `repo:… <id> in:body` | found |

All four returned `total_count: 0` at t+0.3–1.2s and `total_count: 1` at t+16.6–17.4s. So:

- **Marker proof is not vacuous** — the §14.1 dedupe design rests on a real capability, and the
  quoted full-marker query (the one the pipeline sends) is the one that works.
- **There is a real index lag** — an artifact this pipeline created seconds ago is *not* findable.
  Measured once at between 1s and 17s; treat the magnitude as unbounded, not as 17s. A write-time
  `ABSENT` therefore proves "no indexed marker", never "no artifact": it cannot see an artifact
  created inside the lag window, including one this pipeline created and crashed before recording.
  The §14.1 write-time re-search closes the *session-lifetime* staleness window (B8-2 mechanism 2);
  only the reservation lease (mechanism 1) covers the lag window, so both are required and neither
  substitutes for the other.
