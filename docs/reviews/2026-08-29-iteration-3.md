## 2. Findings

Legend: `blocking` = must not ship; `major` = plan violation or state/artifact corruption on a reachable path; `minor` = correctness or observability defect with a bounded consequence; `nit` = hygiene.

### F1 — major — a recorded `pr_url` is treated as "publication complete", so the mandated issue-patch is permanently skipped after any failure in the CI window

- File: `src/pipeline/__main__.py:156-177`, with the trigger in `src/pipeline/__main__.py:293-336` and `src/pipeline/github_client.py:730-737`
- Plan: §7 — "Ordering is mandated, not optional: (1) create the issue, (2) create the PR with `Closes #<n>`, (3) patch the issue body with the PR link"; §14.1 idempotency/resume.
- Code: `_publish_live` resumes with `persisted = state_store.resume(...)` and, when `persisted.pr_url is not None`, appends the row to `published` and `continue`s — with no check of `persisted.state`. Step (3) is executed only inside the same in-process pass that created the PR.
- Trigger: publication reaches `after_pr_created` (row `pr_created`, `pr_url` recorded), then `ci_probe` blocks in `wait_for_required_contexts` for up to the CI deadline. Any exception or process death in that window — a 502 on the body PATCH, a 5xx during polling (the transport retries only 429 and rate-limited 403, `http_transport.py:127-148`), an OOM kill, a CI timeout that raises, an operator `Ctrl-C` — leaves the durable row at `pr_created`. On the next run the candidate is short-circuited at `:175` forever: the issue is never patched with the PR link, the candidate never reaches `issue_patched`, labels and `needs-human-review` are never applied, and auto-merge is never re-evaluated. Because the CI wait is the longest-running step in the pipeline, this is the most likely failure window in the whole run, not an exotic one.
- Fix: gate the resume short-circuit on lifecycle state, not on `pr_url` — skip only when `persisted.state` is `issue_patched`/`comment_created` (or terminal); when the row is `pr_created`, re-enter publication with `existing_pr_number`/`existing_pr_url` so `publish_artifacts` skips `create_pr`, re-probes, and completes the patch. That also makes `publish_artifacts` resumable at step (3), which it currently is not.

### F2 — major — `ci_probe` patches the PR body and drops the `Closes #<issue>` cross-link that `create_pr` wrote

- File: `src/pipeline/__main__.py:314-325`; `src/pipeline/github_client.py:711-716`, `730-737`; `src/pipeline/templates/render.py:73-89`
- Plan: §7 — "cross-linked (`Closes #<issue>` in the PR so merging auto-closes the manager-facing issue)"; §19 `test_crosslink_roundtrip` ("`Closes #n` present, both artifacts carry …").
- Code: `create_pr` is called with `f"{pr_body.rstrip()}\n\nCloses #{issue_number}\n"`. Immediately afterwards `ci_probe` re-renders the body with `render_pr_body(...)` **without** passing `issue_number` — the parameter that produces the `Closes #n` line (`render.py:87-89`) — and PATCHes that body over the PR (`patch_pr_body`, `github_client.py:711-716`). The closure cannot supply it either: `candidate.issue_number` inside `_publish_live` is the *persisted* value, which is `None` on the first run because the issue is created inside `publish_artifacts` and the closure's candidate is never updated.
- Trigger: every LIVE PR publication that gets past the DCO assertion. The final PR body has no `Closes #n`, so merging (including via the auto-merge this same probe authorizes) leaves the manager-facing issue open forever, and §11 burn-down keeps counting it as remaining.
- Fix: pass the issue number into the probe (or have `publish_artifacts` re-append the `Closes #<n>` suffix after the probe's patch) and validate the patched body against the same invariant that the pre-write body was validated against. Better: separate the observation from the mutation — resolve the head SHA and assert DCO in the probe, and do the provenance re-render as an explicit `after_ci` step that owns the full body including the cross-link.

### F3 — major — a degraded-sink run still aborts, and now aborts *after* artifacts have been written

- File: `src/pipeline/__main__.py:152-155`
- Plan: §7 degraded path — "if `has_issues == false` on the target, dispatch aborts **before any write** unless `issue_sink = pr_comment`, in which case the manager-facing artifact is rendered as a dedicated PR comment plus `reports/issues/<candidate_id>.md`". With `issue_sink=pr_comment` (which preflight requires for a degraded run to start at all) the plan sanctions no abort.
- Code: `_publish_live` raises `RunAbort("issues are disabled; issue-only candidates require issue_sink=pr_comment")` for any `action=OPEN_ISSUE` candidate when `config.has_issues` is false. `dispatch_candidates` still assigns `OPEN_ISSUE` to every medium-tier candidate regardless of sink.
- Trigger: `has_issues=False`, `issue_sink=pr_comment`, any medium-tier candidate. The loop publishes high-tier candidates first (issues/PRs/comments created, durable rows written, sessions already paid for) and then dies on the first medium-tier one. `run_once` never reaches `simulate_run` (`:1061`), so no run report, KPI rollup or events file is produced for a run that already mutated the target.
- Fix: for `OPEN_ISSUE` under a degraded sink, render `reports/issues/<candidate_id>.md`, mark the candidate `artifact_degraded` and continue — the plan already names that artifact. If an abort is genuinely intended, it must happen in preflight, before any write.

### F4 — major — the `ClosedPullRequestError` deferral discards the issue number recorded seconds earlier, so the next run creates a duplicate issue

- File: `src/pipeline/__main__.py:401-410`, interacting with `:156-164` and `state.py:130-149`
- Plan: §7 / §14.1 — the issue-created-but-PR-missing state "is the canonical resume case covered by the idempotency spec"; iteration-1 B2 required no duplicate artifacts across runs.
- Code: the handler builds the deferred row from the closure's `candidate`, which does **not** carry the issue number — `after_issue` only appends a row, it does not rebind `candidate`. So the appended row is `deferred` / `capability_unavailable` with `issue_number=None`, `issue_url=None`, and last-write-wins makes it the resume state (`state.resume` → `get` → `latest`, `state.py:90-103`).
- Trigger: a candidate whose branch already has a closed PR (a human closed the previous attempt). Run 1: issue #N created, `create_pr` 422, no open PR, `has_closed_pr_for_head` true → defer. Run 2: `persisted` is non-`None`, so `_publish_live` skips `append_if_new_artifact` entirely (`:157-164`) — the marker search that would have caught the existing issue is never consulted — and publishes a **second** issue for the same candidate. The run report also shows the candidate with no artifact links while issue #N sits orphaned in the target.
- Fix: build every deferral row from the most recent persisted row (or from `candidate.model_copy` with the artifact fields carried forward), and make the resume path consult `existing_artifact`/`marker_exists` whenever the persisted row has no artifact recorded, not only when no row exists at all. The same defect pattern applies to the deferral rows at `:166-173` and `:967-975`, which are also built from pre-publication candidates.

### F5 — major — any publication exception other than `ClosedPullRequestError` aborts the whole run after writes, and takes §11 observability with it

- File: `src/pipeline/__main__.py:368-410`, `1041-1072`; `src/pipeline/http_transport.py:127-149`; `src/pipeline/github_client.py:405-410`
- Plan: §7 (aborts, if any, happen before any write); §11 (every run emits events, KPI rollup and run report); §13/§14 degradation clause (capability failures degrade the candidate, not the run).
- Code: the `try` around publication catches only `ClosedPullRequestError`. `HttpTransportError` from `create_issue`/`patch_issue`/`patch_pr_body`/polling, `ValueError` from `validate_pr_body` inside the probe, `ArtifactUnavailableError`, and `KeyError`/`OSError` from the template reads all propagate out of `_publish_live` and `run_once`, so `simulate_run` never runs and no report/KPI/events are written for a run that has already created remote artifacts. The transport retries only 429 and rate-limited 403 — a single 502 or a connection reset on any of these calls ends the run. `ArtifactUnavailableError` is a bare `RuntimeError` and is not in `main`'s except tuple (`:1097`), so it exits with a traceback rather than the sanitized message.
- Trigger: one 5xx or dropped connection on any publication call for any candidate; or a template that renders a body failing `validate_pr_body` inside the probe (which happens *after* the PR exists).
- Fix: wrap per-candidate publication in a handler that defers the candidate with the appropriate reason and continues the loop (as `M6'` did for sessions), and produce the observability artifacts in a `finally`/outer scope so a partial run still emits its evidence. Add `ArtifactUnavailableError` to `main`'s handled exceptions.

### F6 — major — the fail-closed diff gate is satisfied by an empty `committed_diff`, and the reported diff is never reconciled with the branch

- File: `src/pipeline/session_client.py:553-611`; `src/pipeline/red_baseline.py:174-230`
- Plan: §9.3 / §14 structural invariants — the implementer "commits non-test paths only"; §12.1 `diff_reviewed` is required and an iteration that reviews nothing while the implementer's diff is non-empty is incomplete.
- Code: `implementer_inspection = self.inspect_implementer_diff(implementer_diff)` runs the classifier over the *self-reported* string. For `committed_diff: ""`, `_changed_hunks` yields no hunks, the inspection is `accepted`, `changed_paths` is empty, and `changed_paths <= read_paths` holds for any `files_read` — including `[]`. So the iteration is complete, no `implementer_test_edit` finding is raised, and the candidate can converge and satisfy the auto-merge conjunction. Nothing ever compares `implementer_output["files_changed"]` with the paths in `committed_diff`, and nothing compares either against the branch, even though the client now has `branch_sha`, `pull_request_head_sha` and `commit_message` and could read `GET /pulls/{n}/files`.
- Trigger: an implementer session that edits a test file and reports `committed_diff: ""` (or a diff that simply omits the test hunks) with `files_changed: ["superset/x.py", "tests/test_x.py"]`. The invariant is enforced only against a cooperative report.
- Fix: reject an iteration whose `files_changed` is non-empty while `committed_diff` parses to zero changed paths, or whose `files_changed` is not a subset of the diff's changed paths; and reconcile the reported diff against the actual branch (`GET /repos/{o}/{r}/pulls/{n}/files`, or `compare/{base_sha}...{head_sha}`) before convergence, treating a mismatch as blocking.

### F7 — minor — two durable rows per completed write, and the intermediate rows omit fields the resume path needs

- File: `src/pipeline/__main__.py:338-366`, `443-460`, `657-701`
- Plan: §14.1 lifecycle — one row per completed write, append-only, last-write-wins.
- Code: `after_issue_patched` appends `issue_patched` and then `published_candidate` appends `issue_patched` again for the same write; the degraded path appends `comment_created` twice the same way; `_prepare_live_candidate` appends the same `dispatching` row twice when a prior row exists (`:685` and `:701`). ### F8 — minor — closed/merged discrimination is wrong, and a merged PR is deferred as a capability failure

- File: `src/pipeline/github_client.py:578-609`, `717-729`; `src/pipeline/__main__.py:401-410`
- Plan: §14.1 terminal states; §11 merge accounting.
- Code: `get_pr_for_head` requests `state=all` and filters `state == "open"`; `has_closed_pr_for_head` repeats the identical request and matches `state in {"closed", "merged"}`. The GitHub REST API does not return `"merged"` as a pull-request `state` — a merged PR is `state: "closed"` with `merged_at`/`merged` set (this is API behaviour I did not exercise here; it is documented, but treat it as unverified against the live API in this review). So the merged case is caught only incidentally by `"closed"`, and a merged PR — i.e. a landed remediation — is reported as `capability_unavailable` and deferred, which is the wrong terminal outcome and, via **F4**, also loses the issue linkage.
- Trigger: re-running over a candidate branch whose PR was merged or closed.
- Fix: make one list call, classify from `state` plus `merged_at`, treat merged as a successful terminal state (`converged`/`terminal` with the PR recorded), and treat closed-unmerged as `human_review` rather than a capability failure.

### F11 — minor — the `diff_reviewed` head-SHA comparison is inert in LIVE while SIMULATE injects a value that makes it pass

### F13 — minor — quarantine can silently drop a valid row, and the resume it protects then depends on a search that may be unavailable

- File: `src/pipeline/state.py:62-83`, `118-127`, `130-149`
- Plan: §14.1 durable state and resume.
- Code: `_read_rows` quarantines any line that fails `Candidate.model_validate` (pydantic `ValidationError` is a `ValueError`, so schema drift is caught by the same handler as truncation), appends it to `<path>.corrupt`, and continues. The only signal is a count in the run report (`__main__.py:1039-1040`). `_quarantine_seen` is seeded once per store and keyed on the whole line, so it grows with the corrupt file and never sees concurrent appends by another process — two concurrent runs can write the same corrupt line twice (harmless) but also both conclude "no state" for a candidate.
- Trigger: a schema change (a new required field, a removed enum value) invalidates previously valid rows — exactly the situation this branch keeps creating. Resume then falls back to `marker_exists`, which returns `False` and sets `marker_search_failed` on any search error (`:118-127`), so a rate-limited or indexing-lagged search yields duplicate artifacts with only a report note.
- Fix: distinguish unparsable lines (quarantine) from schema-invalid ones (fail the run, or migrate), and treat `marker_search_failed` as a hard stop for first-write reservations rather than a note.

### F15 — nit — container UID/output-directory mismatch

- Observed: the image creates `pipeline` (uid 10001) and `chown`s `/output` to it, but compose overrides the user to `${PIPELINE_UID:-1000}`, so the in-image ownership is irrelevant and writes depend entirely on the host bind mount's permissions.
