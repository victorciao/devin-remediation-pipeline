## 1. Findings

### B9-1 — blocking — the new `StatePreservationError` enforcement fires on the ordinary PR-creation write, wedging every LIVE PR candidate *after* the issue and PR exist

- Mechanism: `head_sha_holder` is initialised `[None]` (`src/pipeline/__main__.py:469`) and is only
  filled by `ci_probe` (`:539`). `publish_artifacts` calls `after_pr_created` **before** `ci_probe`
  (`src/pipeline/github_client.py:788-792`). `after_pr_created` appends a `PR_CREATED` row with
  `"head_sha": head_shas[0]`, i.e. `None` (`__main__.py:502`). The row that is already persisted at
  that moment — the reservation (`:249-256`) and then the `ISSUE_CREATED` row (`:365-375`) — carries
  the reviewed head, because a converged LIVE candidate always has `head_sha` set (phase B resolves
  it and refuses without it: `session_client.py:1084-1100`; carried into the candidate at
  `__main__.py:1667`). `_append_locked` therefore sees `previous is not None and current is None`
  for `head_sha` and raises `StatePreservationError` (`src/pipeline/state.py:271-276`). That
  exception is caught by the per-candidate handler (`__main__.py:739-766`) and the candidate is
  written `deferred` / `capability_unavailable`.
- Plan clause violated: §14.1 (`docs/IMPLEMENTATION_PLAN.md:918-922`) — "No write may replace a
  non-`None` durable identity with `None` — `StatePreservationError` is the enforcement point";
  §14.1:924-927 — `capability_unavailable` is reserved for actual capability loss; §7 artifact
  ordering (issue → PR → issue patch).
- Scenario in LIVE: the first PR candidate on `victorciao/superset`. The issue is created, the PR is
  created with `Closes #n`, then the very next state write raises. Consequences: the issue is never
  patched with the PR link, `after_ci` never runs so the PR body keeps the pre-CI rendering with no
  commit provenance, no labels are applied (`:767-780` is after the `try`), and `needs-human-review`
  — mandatory in `ci_evidence_mode=local` (`:309-313`) — is never applied to a PR that a human must
  now review. The wedge is permanent, not transient: the next run finds a row with `issue_url`, so
  `decide_resume` returns `RESUME_AT_STEP`/publication (`state.py:86-90`), publication adopts the
  existing issue and PR, `after_pr_adopted` → `after_pr_created` (`__main__.py:515-521`) writes
  `head_sha=None` again, and the candidate defers again with the same false reason. Every LIVE PR
  candidate ends as `deferred/capability_unavailable` while a real, unlabelled, uncross-linked PR
  sits open on the fork.
- This is iteration 8's **M8-4** with its symptom moved: the silent overwrite became a caught
  exception, and the exception now destroys the publication it was added to protect.
- Smallest fix I would accept: in `after_pr_created` (and `after_issue_patched`, `:633`, and
  `after_comment_created`, `:655`) write `head_shas[0] or candidate_for_callback.head_sha`. Keep the
  store-level enforcement exactly as it is — it is doing its job.

### B9-2 — blocking — phase-B correlation can never succeed, because the sent-message timestamp is read only from a response body the API does not return

- Mechanism: `poll_session_after_message` accepts output only when `_message_processed(...)` is true
  (`src/pipeline/session_client.py:598-616`), and `_message_processed` returns `False` immediately
  when `sent_timestamp is None` (`:335-336`). `sent_timestamp` comes from
  `_sent_message_timestamp(message_response)` (`:589`, helper `:308-325`), whose only input is the
  body of `POST /v1/sessions/{id}/message` (`send_message`, `:561-573`): it looks for a top-level
  `message_id`/`id` plus `created_at`/`timestamp` (`_message_marker`, `:286-294`), then for a
  `messages` array **inside that POST body** — a field only `GET /v1/sessions/{id}` ever returns.
  `docs/api-probe-2026-08-30.md` P-2 records that the message endpoint answers `200` with a **null
  body**. `_JsonHttpTransport._request` maps an empty body to `{}`
  (`src/pipeline/http_transport.py:125-126`) and a literal `null` body to `None`, which
  `UrllibDevinTransport.post` rejects as a non-object (`:167-169`). So in LIVE either `send_message`
  raises `HttpTransportError`, or `sent_timestamp` is `None` for every candidate and no phase-B
  answer is ever accepted — the transcript P-3 proves is always complete is never consulted for the
  sent side.
- Plan clause violated: §12.2 (`:705-708`) — correlation is against "the `user_message` that
  delivered the phase-B request" in the session's `messages` array, which P-3 proves is always
  present and complete; the plan nowhere licenses taking that timestamp from the POST response.
- Scenario in LIVE: every candidate. The poller spins for the full reviewer `session_timeout_s`
  (default 5400 s, `src/pipeline/config.py:31`) and raises `PhaseBCorrelationTimeoutError`, which
  `__main__.py:1588-1636` records as `deferred` / `phase_b_correlation_unavailable` — or the
  `HttpTransportError` variant records `capability_unavailable`. A first LIVE run therefore spends
  three real sessions per candidate, publishes nothing, and reports a Devin-API capability failure
  that is actually a client-side defect. This is fail-closed, so it is not a safety hazard; it is a
  throughput and truthfulness blocker, and it is the reason B9-3 is currently masked.
- Relation to iteration 8: **B8-1**'s fail-open fallback is genuinely deleted, but the replacement
  cannot ever accept a correct answer. The defect moved from fail-open to always-refuse.
- Smallest fix I would accept: derive the sent timestamp from the transcript instead of the POST
  body — after `send_message`, `GET /v1/sessions/{id}` and take the greatest `user_message`
  timestamp not present in `previous_message_timestamps`; if no new `user_message` appears within a
  bounded wait, *then* refuse with `phase_b_correlation_unavailable`. Keep `_message_processed`
  unchanged.

### B9-3 — blocking — the phase-A protocol violation is scrubbed only from the local copy, so the same unrequested object is what the phase-B validator re-reads

- Mechanism: when the reviewer emits a valid `diff_reviewed` before the phase-B message, `phase_b`
  records the violation and removes the key from a **local copy** of the snapshot payload
  (`session_client.py:1101-1120`). The server-side `structured_output` still contains it, and P-2
  records that `structured_output` merges keys across messages. `poll_session_after_message` then
  compares the freshly fetched output against the *scrubbed* snapshot (`:588`, `:597`), so
  `changed_output` is satisfied by the scrub itself — the session need not have produced anything
  new. If any `devin_message` postdates the phase-B request (a prose acknowledgement is enough),
  `_candidate_diff_review_matches(first, candidate)` re-reads the merged payload, finds the
  phase-A object, and phase B "converges" on a diff review the reviewer produced while diff-blind
  (`:1152-1153`).
- Plan clause violated: §12.1/§13 (`:530-532`) — "no convergence without a recorded phase-B diff
  review"; §12.2 (`:709-714`) explicitly names this shape: the reviewer "can emit a well-formed
  object unprompted (P-2 key merging)" and that must not license acceptance.
- Scenario in LIVE: any reviewer session that resolves the branch head itself in phase A — plausible,
  since the phase-A prompt gives it the branch and base SHA — and then replies to the phase-B message
  with prose. Currently unreachable only because B9-2 makes `processed` always false; fixing B9-2
  without fixing this turns it on.
- Also incomplete on its own terms: the violation is detected only when the premature object is
  *valid* (`:1101`). A premature but malformed object is neither scrubbed nor recorded, so
  `phase_b_protocol_violation` understates violations.
- Smallest fix I would accept: capture the phase-A `diff_reviewed` value (whatever its shape) before
  sending phase B, and reject any phase-B answer whose `diff_reviewed` is identical to it —
  acceptance must require an object that changed *after* the correlated `devin_message`. Comparing
  `changed_output` against the *unscrubbed* snapshot is the minimum second half.

### B9-4 — blocking — publication eligibility is decided by `action` alone, so candidates that never converged are published

- Mechanism: `_publish_live` selects candidates on `candidate.action in {OPEN_PR, OPEN_ISSUE,
  REVIEWER_ONLY_DIFF}` (`__main__.py:183-189`) and never consults `state`. The role-loop failure
  handler sets `state=TERMINAL` (for `BranchNotAdvancedError` / `DiffReviewIncompleteError`) or
  `state=DEFERRED` (session ceiling, `SessionBlockedError`, `PlannerOutputError`,
  `PhaseBCorrelationTimeoutError`, transport errors) but leaves `action` at `OPEN_PR`
  (`:1575-1636`). Those rows are appended to `reviewed`, persisted (`:1761-1762`) and handed to
  `_publish_live`. `decide_resume` now returns `RESUME_AT_STEP`/publication for a `TERMINAL` row
  without an artifact link (`state.py:76-83`) and for a `DEFERRED` row with no artifact and an
  available marker search (`:86-90`), so the candidate is reserved and published: issue + PR, with
  `diff_reviewed=false` and no red-baseline evidence.
- Plan clause violated: §2 step 4 (`:73`) — "push PR(s) … only after phase B converges"; §9 step 5
  (`:429-432`) — a cap hit or unresolved disagreement goes to `needs-human-review`, not to a PR;
  §13 structural invariants (`:530-532`).
- Scenario in LIVE: a candidate whose reviewer session exhausts its corrective exchange
  (`DiffReviewIncompleteError`) or whose run hits the session ceiling after the implementer already
  pushed. The branch has commits, so `create_pr` succeeds and the fork receives a remediation PR
  whose body renders `diff_range: <base>..<head>` for a review that never validated. Under B9-2,
  *every* candidate takes this path, which makes the first LIVE run's expected outcome "publish an
  unreviewed PR for every candidate".
- Note on iteration 8: **B8-3**'s fix (skip requires artifact proof) is what turned the `TERMINAL`
  half of this on; the `DEFERRED` half predates it. The finding's wording was satisfied and the
  described path moved.
- Smallest fix I would accept: make publication eligibility require a publishable state as well as a
  publishable action — publish only when the row is `CONVERGED`, a post-publication state, or a
  `TERMINAL`/`REVIEWER_ONLY_DIFF` stale skip; and set `action=HUMAN_REVIEW` on the terminal/deferred
  role-loop failure rows (`:1607-1633`) so routing and state agree.

### M9-1 — major — the reservation lease does not cover the work it is supposed to cover

- Mechanism: every LIVE candidate is reserved in the preparation pass (`__main__.py:1445-1460` →
  `_prepare_live_candidate:1129`), which runs to completion for *all* candidates before any role
  session starts (`:1486`). The lease is `reservation_lease_s`, default `3 × 5400 s`
  (`config.py:238-243`), and nothing refreshes it between preparation and publication: the interim
  writes go through `append()` (`state.py:285-291`), which does not touch `reserved_at`. Per
  candidate the covered work is a planner session plus up to `iteration_cap` (default 5) rounds of
  concurrent implementer/reviewer sessions plus up to two phase-B polls, each bounded by
  `session_timeout_s` — and every later candidate additionally waits for all earlier candidates.
- Plan clause violated: §14.1 (`:906-910`) — the reservation is the mechanism that "bars a second
  writer outright … since the row it writes has no artifact link yet"; §14.1:899-904 states the
  marker re-search cannot substitute, because the search index lags by an unbounded amount
  (`docs/api-probe-2026-09-01.md` P-6).
- Scenario in LIVE: run A reserves candidates 1..8 at t0; candidate 8's sessions start hours later.
  Run B starts after the lease expires, finds the claim stale, reclaims it, and its write-time marker
  search returns `ABSENT` (correctly — nothing is published yet, and even if something were, the
  index lag hides it). Both runs then perform the first artifact write for candidate 8: two issues,
  two PRs, two branches with the same `candidate_id`. This is exactly the property the brief names.
- Smallest fix I would accept: renew the claim immediately before the first write of each phase —
  call `append_if_new_artifact` (same `run_id`) at the top of the per-candidate session loop and
  again at the top of the per-candidate publication block (the publication renewal already exists at
  `:256`), and reserve per candidate at the point of use rather than for the whole batch up front.
  A lease that is renewed cheaply is strictly better than a longer default.

### M9-2 — major — a claim whose `reserved_at` is in the future is never reclaimable

- Mechanism: `append_if_new_artifact` treats a negative age as "an unexpired lease" and refuses
  unconditionally, with no upper bound (`state.py:322-328`).
- Plan clause violated: §14.1 (`:908-910`) — "after which a crashed run's claim **may be
  reclaimed**"; the plan's expiry is a bounded quantity, so a claim that never expires contradicts it.
- Scenario in LIVE: any clock skew on the writer (a container with a fast clock, an NTP step, or a
  hand-edited/quarantine-restored row) permanently parks the candidate. Every subsequent run defers
  it `reservation_held`, forever, and the KPI reports it as a live contention rather than a stuck row.
- Smallest fix I would accept: treat `reserved_at > now + reservation_lease_s` as invalid — log it
  and reclaim — and keep the "unexpired" reading only for small negative skew (e.g. within the lease).

### M9-3 — major — `StatePreservationError` in `_prepare_live_candidate` aborts the whole run instead of deferring one candidate

- Mechanism: the preservation guard raises inside `_prepare_live_candidate`
  (`__main__.py:1180-1195`); the caller (`:1449-1456`) has no `try`, `run_once` does not catch it,
  and `main`'s handler list (`:1865-1872`) covers `ArtifactUnavailableError`, `ConfigError`,
  `HttpTransportError`, `RunAbort`, `ValueError`, `OSError` — not `StatePreservationError` (a
  `RuntimeError`). The run dies with a traceback: no report, no KPI rollup, no event log, and every
  already-reserved candidate keeps a live claim.
- Plan clause violated: §14.1 (`:924-927`) — "A per-candidate failure defers that candidate only";
  §11 "no candidate unaccounted".
- Scenario in LIVE: any row shape the guard is meant to catch (a persisted `issue_url` that the
  prepared row does not carry — e.g. after the marker-adoption path or a quarantined/rewritten state
  file). The guard exists precisely because the author thinks that state is possible; its handling
  is the maximally destructive one.
- Smallest fix I would accept: wrap the `_prepare_live_candidate` call per candidate, defer that
  candidate with a specific reason, and add `StatePreservationError` to `main`'s handled set so the
  process exits 1 with a sanitized message rather than a traceback.

### M9-4 — major — a duplicate suppressed by marker proof is recorded as `capability_unavailable`

- Mechanism: for a candidate with no persisted row whose marker search finds the artifact,
  `decide_resume` returns `RESUME_AT_STEP`/publication (`state.py:72-75`, `artifacts_present=True`).
  The publication loop then calls `append_if_new_artifact`, which correctly refuses because the
  marker was found — but leaves `reservation_reason = None` (`state.py:311-312`), so
  `__main__.py:263-279` writes the candidate `deferred` with `ReasonCode.CAPABILITY_UNAVAILABLE` and
  `reason_detail=None`.
- Plan clause violated: §14.1 (`:924-927`) — `capability_unavailable` "never asserted over" a
  non-capability outcome; §11/§19 honesty; §14 idempotency accounting (a suppressed duplicate write
  is the *success* case of dedupe, not a failure).
- Scenario in LIVE: an `OPEN_ISSUE` (medium-tier) candidate whose issue already exists from a prior
  run whose state file was lost or rotated — and any candidate published by a run that crashed
  before recording. The operator reading the KPI sees "the platform was unavailable" for a candidate
  whose artifact is sitting in the target repo.
- Smallest fix I would accept: set `reservation_reason = "artifact_exists"` on that return, add the
  matching reason code, and treat it as `SKIP` with the adopted artifact rather than a deferral;
  `decide_resume` should return `SKIP` (or an adopt action) when `persisted is None` and
  `artifacts_present` is true.

### M9-5 — major — the burn-down never counts a published candidate, and `dispatched_pr` hides real PRs

- Mechanism: `compute_burndown` counts progress only for rows in state `CONVERGED` (or `TERMINAL` +
  `STALE_SKIP`) that carry an artifact (`src/pipeline/observability/kpis.py:65-75`). A fully
  published candidate ends in `ISSUE_PATCHED` (`__main__.py:827-837`), so progress is structurally
  always 0 in LIVE, and `active`/`completed` (`kpis.py:150-157`) classify it as *active*.
  Separately, `dispatched_pr`/`dispatched_issue` exclude any row in `DEFERRED`
  (`kpis.py:87-94`), so the PR that B9-1 leaves open counts as zero PRs dispatched.
- Plan clause violated: §11 KPI definitions and §19 — the reported numbers must not understate work
  done or capability loss; §11 "no candidate unaccounted".
- Scenario in LIVE: the first successful run reports "codeql: 0/N complete" and `dispatched_pr: 0`
  while N PRs exist on the fork. That is the single most misleading pair of numbers a first run can
  print, and it points the operator at the wrong system.
- Smallest fix I would accept: count `ISSUE_PATCHED`/`COMMENT_CREATED`/`PR_CREATED`-with-artifact as
  burn-down progress and as `completed`; count `dispatched_pr` from `pr_url is not None` regardless
  of the terminal lifecycle state, and report deferred-with-artifact separately.

### m9-1 — minor — `iterations` uses `max()`, so review rounds and phase-B exchanges never add up

- `__main__.py:1662-1665` sets `iterations = max(review.iterations, phase_b_exchanges)`, and the
  orchestrator caps exchanges at `iteration_cap` (`session_client.py:1235`). §12.2 (`:724-726`) says
  "Each phase-B exchange counts as an iteration, so `iterations` reflects the sessions actually
  spent". Two review rounds plus two phase-B exchanges are reported as 2. Fix: sum the two counters
  (still clamping the report, not the underlying count, if a cap is wanted).

### m9-2 — minor — timestamp correlation compares ISO strings lexicographically

- `_message_processed` (`session_client.py:344`) and `_sent_message_timestamp` (`:325`) order
  timestamps with `>` / `max()` on raw strings. P-3's observed format (`…+00:00`, microseconds) is
  self-consistent, but any `Z` suffix, offset change or precision change silently breaks ordering and
  the candidate defers `phase_b_correlation_unavailable`. Fail-closed, so minor. Fix: parse with
  `datetime.fromisoformat` and compare instants.

### m9-3 — minor — `rerun`'s already-attempted short-circuit is unreachable in LIVE, and returns a stale iteration if it ever is reached

- `session_client.py:1197-1201` returns the *same* iteration when the current reviewer session
  already had its phase B and still does not validate. In LIVE `phase_b` either returns a validated
  result or raises `DiffReviewIncompleteError` (`:1185-1190`), so the branch is dead; if a future
  change makes it live, `run_review_loop` will call `rerun` again on an unchanged iteration and burn
  loop ordinals without work. Fix: delete it, or raise the same terminal error.

### m9-4 — minor — `escalated` counts converged stale skips as failed-review escalations

- `kpis.py:177-180` and `observability/report.py:68-72` count any `TERMINAL` row with a reviewer
  session id. A stale skip is `TERMINAL` + `STALE_SKIP` + converged (`review_loop.py:294-297`), so
  the "Failed review escalation" section lists successes. Fix: exclude `reason is STALE_SKIP` (or
  require `needs_human_review`).

### m9-5 — minor — no KPI or report line for `writes_suppressed` / `artifact_simulated`

- SIMULATE stamps rows and bodies truthfully (`state.py:268-269`, `simulation.py:53`, `:123-124`,
  `templates/render.py:105-108`) and the KPI title says "SIMULATED"
  (`kpis.py:293-297`), but no metric counts suppressed writes or simulated artifacts, so a SIMULATE
  rollup and a LIVE rollup differ only by a title and a mode line. §11 asks for the distinction to
  be legible. Fix: emit `writes_suppressed` and `artifact_simulated` counts in `compute_kpis`.

### n9-1 — nit — `reservation_reason` is a bare string threaded through `ReasonCode(...)` lookups

- `__main__.py:264-277` reconstructs a `ReasonCode` from `state_store.reservation_reason` by
  membership test against the enum's values. A typo in `state.py` degrades silently to
  `capability_unavailable`. Fix: make `reservation_reason` a `ReasonCode | None`.

### n9-2 — nit — `_publish_live`'s `reason_detail` defaults to the marker outcome

- `__main__.py:223-228` sets `reason_detail = candidate.reason_detail or marker_outcome.value`, so a
  candidate with no problem at all carries `reason_detail="absent"` into the published row and the
  event log. It reads like a defect record for a healthy candidate.
