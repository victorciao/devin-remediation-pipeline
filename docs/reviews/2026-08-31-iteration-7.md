### B7-1 — blocking — a *successful* marker search that finds nothing is reported as "search unavailable", so every fresh candidate is deferred before any session

- File: `src/pipeline/state.py:222-230` (`marker_search_unavailable`), `:197-216` (`marker_artifact`), `:253-261`; callers `src/pipeline/__main__.py:961-972` and `:217-231`.
- Plan: §14.1 idempotency/resume ("re-runs must not open duplicate PRs/issues … the pipeline re-reads state **and** searches the target repo for the marker", §17), §11 "no candidate unaccounted", §13 fail-closed.
- Observed: `a9e30be` changed `_marker_results` from `dict[str, bool | None]` to `dict[str, MarkerArtifact | None]`, so "searched, found nothing" and "search failed" now share the value `None`. `marker_search_unavailable` was written for the old sentinel and still reads `self._marker_results.get(candidate_id) is None`, so a healthy zero-result lookup is classified as *unavailable*. Executed: with `marker_search=github_marker_search(lambda _: {"total_count": 0, "items": []})`, `marker_search_unavailable` → `True`, `resume_decision` → `DEFER`, `append_if_new_artifact` → `False`.
- Trigger: LIVE, every lane, every candidate that does not already have an artifact — i.e. all of them on a first run. In LIVE `marker_search` is always configured (`__main__.py:1094-1105`, `github_transport` is non-`None`), so `_prepare_live_candidate` reaches `decision.action is DEFER` at `:964` and appends `deferred/capability_unavailable` *before* the planner session. A first LIVE run therefore does no work at all, and the stated reason is false: the capability was available and the answer was "no artifact exists".
- The inverse polarity is in the same predicate: `candidate_id not in self._marker_search_unconfigured` means "we never looked" evaluates to *available*, i.e. `artifacts_present=False` is trusted and publication proceeds. Today no LIVE path leaves `marker_search` unset, so this is latent — but it is exactly the "cannot prove absent → presumed absent" inversion, and it is one refactor away from opening a duplicate issue.
- Fix: keep the three states distinct instead of overloading `None`. Record per-candidate outcome as an explicit enum (`FOUND` / `ABSENT` / `FAILED` / `ORPHANED` / `UNCONFIGURED`) set in `marker_artifact`, have `marker_search_unavailable` return true only for `FAILED`, and make `UNCONFIGURED` return **true** as well (never looked ⇒ not proven absent) so the fail-closed direction matches the plan. Add the zero-result case to whatever asserts the reservation contract.

### B7-2 — blocking — `append_if_new_artifact` deadlocks against its own file lock

- File: `src/pipeline/state.py:238-269` (`append` takes `LOCK_EX` at `:242-243`; `append_if_new_artifact` holds the same lock at `:263-264` and then calls `append` at `:268`).
- Plan: §14.1 durable append-only state as the dedupe/resume source of truth; §12/§14 recoverability.
- Observed: `a9e30be` added locking to `append` but left the reservation path calling it while already holding the lock. Each `open()` creates a new open file description, so `flock` on the second descriptor blocks even inside one process. Executed: with an unconfigured marker search (which passes the `:257-261` guard), `append_if_new_artifact` never returned; an 8-second `SIGALRM` killed the process.
- Trigger: any call to `append_if_new_artifact` that reaches `:263`. Today **B7-1** short-circuits every LIVE call at `:257-261` or earlier, so the hang is masked — the two defects hide each other, and fixing B7-1 alone converts "everything defers" into "the run hangs on the first reservation with no timeout, no log line and a partially written state directory".
- Fix: split the writer — a private `_append_locked(candidate)` that assumes the lock, called both by `append` (which acquires it) and by `append_if_new_artifact` (which already holds it). A reentrancy guard on the store would also work; a recursive `flock` will not.

### B7-3 — blocking — the phase-B acceptance predicate is never communicated to the only party that can satisfy it

- File: `src/pipeline/prompts.py:242-258` (the phase-B prompt), `src/pipeline/session_client.py:106-131` (`validated_diff_review`), `:132-148` (`_candidate_diff_review_matches`), `:577-596` (`PHASE_B_REVIEWER_OUTPUT_SCHEMA`, exported at `:1034`, never sent), `:952-985` (`phase_b`), `:454-487` (`poll_session_after_message`).
- Plan: §9 step 4 and §12.1 — `diff_reviewed { base_sha, head_sha, files_read[] }`; §2 "convergence requires a recorded phase-B diff review"; §12.1 "a reviewer response that omits it, or that names no files while the diff changed files, is not a review".
- Observed: convergence requires `diff_reviewed` to be a **mapping** with a non-empty `base_sha`, a non-empty `head_sha` **equal to the SHA the orchestrator just read from GitHub**, and a `files_read` list that is a superset of the paths in the implementer's `committed_diff`. The phase-B prompt says only "Set diff_reviewed true only after actually reading the diff" — it does not state the object shape, does not quote the expected `head_sha`, and does not say `files_read` must enumerate every changed file. The schema written for precisely this contract, `PHASE_B_REVIEWER_OUTPUT_SCHEMA`, is dead code: `send_message` (`:440-452`) posts a bare `{"message": …}`, and the session's structured-output schema was fixed at creation to the phase-A one.
- Trigger: LIVE, every candidate, first iteration. A cooperative reviewer answering `diff_reviewed: true` fails `isinstance(value, Mapping)`; one answering with an object but `files_read` listing only what it *reviewed by hunk* fails the superset test; one answering with its own idea of `head_sha` (e.g. its local commit rather than the branch head after the rebase-push) fails the identity test. Each failure yields the blocking finding path, one rerun, then `terminal / diff_review_incomplete` with `iterations=0` — the dry-run signature. A reviewer that answers in prose without updating structured output is worse: `poll_session_after_message` requires a *changed* `structured_output`, so the candidate burns the full `session_timeout_s` and lands in `deferred/capability_unavailable`.
- Fix: state the contract where it is enforced. Render the required object verbatim in the phase-B prompt, including the exact `base_sha` and the resolved `head_sha` the pipeline will compare against, and the rule "`files_read` must list every path in the diff above". Pass `PHASE_B_REVIEWER_OUTPUT_SCHEMA` on the phase-B message (or re-assert it) so the shape is machine-enforced rather than hoped for; if the API cannot re-scope a schema mid-session (§4), fall back to a fenced JSON block plus a parse of the message body. Separately, accept `files_read` covering the changed paths *or* an explicit `read_full_diff: true`, so an honest reviewer of a 200-file diff is not forced into an enumeration it cannot produce.

## 4. Open questions only a real GitHub or Devin API call can settle

1. **Can a session's structured-output schema be re-scoped mid-session?** B7-3's cleanest fix sends `PHASE_B_REVIEWER_OUTPUT_SCHEMA` with the phase-B message. If `POST /v1/sessions/{id}/message` accepts no schema, the contract must be enforced by prompt + parse instead, and `poll_session_after_message` needs a different completion signal.
2. **What does a session that has already emitted structured output do when messaged?** Does `status` leave `finished` (so a transition can be observed), and does `structured_output` get replaced or merged? m7-5's correlation fix and the whole phase-B poll depend on the answer, as does whether a prose-only reply can be detected before `session_timeout_s`.
3. **Does the Devin API expose a per-message id or an `updated_at` on the session?** Without one, "this output answers this message" is unprovable and phase B stays inferential.
4. **What does `GET /search/issues` return for a repository with zero matches, and does the fork's token see it?** B7-1's fix must distinguish zero results from a 403/422/rate-limit; the shape of the failure response decides whether `ValueError` (orphaned) or the generic handler (failed) is the right classification.
5. **Whether two concurrent role sessions can both `pull --rebase`/push the same branch without one being rejected past its retry budget** — the branch contract in `prompts.py:54-63` is unverified against real GitHub ref-update contention, and B-2's closure rests on it.
6. **Whether `victorciao/superset` resolves `ci_evidence_mode` to `local` or `github`** on the day of the run (one lifetime Actions run). It decides which evidence path and which PR-body validation apply, and therefore whether M7-1 blocks the run.

A single controlled dry run against one candidate would settle 1–4 and, if the reviewer is asked for the phase-B object explicitly, 5 as well. I would not spend a dry run on 6; it is a two-request read the lead can do without a pipeline run.
