## 2. Findings

### M-1 — major — branch preparation defeats the consolidated resume: a `pr_created` row is rebuilt without its PR identity and then deferred permanently

- File: `src/pipeline/__main__.py:885-935` (with `:1136-1139` and the removed early return), `src/pipeline/state.py:38-70`
- Plan: §14.1 — durable lifecycle state and "a re-run resumes durable state and completes the partial artifact set"; §7 issue → PR → issue-patch ordering.
- Code: `decide_resume` correctly returns `RESUME_AT_STEP("publication")` for a `pr_created` (or `deferred`-with-artifacts) row. `_prepare_live_candidate` acts on that decision by rebuilding the candidate: `prepared = candidate.model_copy(update={state: dispatching, base_sha, head_branch, issue_number, issue_url})` — the base is the freshly enumerated candidate, so `pr_url`, `pr_number`, `head_sha`, `comment_url` and `merged_at` are dropped, and the row appended at `:918-919` erases the PR identity from the state file. It then calls `create_branch`, gets 422, compares `branch_sha(branch)` against the recorded `base_sha`, and — because the branch carries the previous run's implementer commits — takes the mismatch branch and appends a `deferred`/`capability_unavailable` row built from that stripped `prepared`. Every later run repeats the sequence, so the candidate never re-enters publication.
- Trigger: two reachable windows, both of which the consolidation exists to cover.
  1. Anything that ends the process between `create_pr` and `patch_issue` (the CI wait is up to `ci_wait_timeout_s`): the issue is never patched with its PR link, and the state file loses the only record of the PR number.
  2. Anything that ends the process after the implementer's first commit but before the issue write: no artifact exists at all, yet the candidate is permanently `capability_unavailable` — the branch is *ours*, and being ahead of `base_sha` is the expected condition on resume, not a conflict.
  Note `run_once:1136` also depends on the stripped fields: because `prepared.pr_url` is now `None` and the state is `dispatching`, a candidate with a live PR is routed back into fresh planner/implementer/reviewer sessions rather than into publication, so the resume also re-spends the session and ACU budget §12 caps.
- Fix (three small changes): carry the artifact fields forward in `prepared` (copy from `persisted` and update only `state`/`base_sha`/`head_branch`); treat a 422 whose existing head is a *descendant* of the recorded `base_sha` as a resume rather than a conflict (`commit_messages_between(base_sha, existing_sha)` is already available and non-empty exactly in that case), keeping the mismatch deferral for a branch at an unrelated base; and build the 422 deferral row from `persisted or prepared` so PR identity survives even when it does defer. With those, route a resumed candidate whose PR exists straight to publication as before.
- Note: this is the fourth iteration in which this crash window is the top finding, and the third distinct mechanism. The decision function itself is now good; the defect is that `_prepare_live_candidate` does not honour it — it discards the state the decision was made about. I would add one assertion at the end of `_prepare_live_candidate` — the returned candidate must not have fewer recorded artifacts than `persisted` — which mechanically forecloses this whole family.

### M-2 — major — the CI wait cannot detect the fork approval gate it was narrowed for, and burns the full timeout per candidate in `local` mode

- File: `src/pipeline/github_client.py:213-241` (`_required_context_statuses`), `:289-321` (the wait loop), `src/pipeline/__main__.py:424-436`
- Plan: §10.1 — "A fork PR sitting in **pending workflow approval** … reports no context and therefore keeps the mode at `local`; that state is recorded as `ci_evidence_unavailable: awaiting_workflow_approval`"; §10 `ci_wait_timeout_s` semantics.
- Code: `awaiting_approval` is computed from the `statuses` map, but `_required_context_statuses` records a check run **only when `conclusion` is a string** (`:230-231`) and legacy statuses only from `state`. A workflow held by the first-time-contributor / fork gate produces *no check runs at all* — and, where it does produce one, `waiting`/`queued` is a `status`, never a `conclusion`, while legacy commit statuses only ever carry `pending`/`success`/`failure`/`error`. So the detection can fire only on a literal `action_required` **conclusion** (the deployment-approval case), not on the gate §10.1 names. `e35cccb` was right that `pending`/`queued` made the loop dead, but the narrowed set moved the problem rather than solving it: the held-workflow case now falls through to `sleep(15)` until the deadline and returns a bare `ci_evidence_unavailable` with no `awaiting_workflow_approval` detail.
- Consequence for a real run: `elapsed_s=0` is passed per candidate, so with the default `ci_wait_timeout_s=5400` every PR candidate polls for 90 minutes before being recorded unavailable — serially, and unconditionally, because `ci_probe` calls the wait whenever `wait_for_ci=True` regardless of the current evidence mode. A first LIVE run with three PR candidates on a fork whose workflows are held therefore takes ~4.5 hours to reach its report, and the §10.1 evidence distinction between "held for approval" and "never reported" is absent from the artifacts.
- Fix: read `status` as well as `conclusion` in `_required_context_statuses` (record `f"status:{status}"` or a separate map) and treat a required context with `status in {queued, waiting, in_progress}` and no conclusion as in-flight, versus `action_required`/`waiting` as held; additionally treat "zero required contexts reported after the first poll interval and the PR is from a fork" as `awaiting_workflow_approval`. Independently, cap the total CI wait across a run (thread `elapsed_s` through, as the parameter already anticipates) so one run cannot spend N × `ci_wait_timeout_s`.

## 3. Answers to the specific questions

**Is the auto-merge move a weakening?** No — I agree with your reading, and the stronger statement holds: no path reaches `enable_auto_merge` on evidence weaker than an observed all-green report. Proof by the only chain that reaches it. `publish_artifacts:707-718` requires `candidate.auto_merge_eligible` (set only by `dispatch` and narrowed monotonically by `apply_review_result:272`), `config.auto_merge_enabled`, `ci_result is not None`, `ci_result.mode is CiEvidenceMode.GITHUB`, `ci_result.auto_merge_eligible`, `ci_result.reason is None`, and test evidence. `ci_result` can only come from `ci_probe`, which is a required argument (`:668-669`) and is called unconditionally before the gate (`:702`). Every `ci_probe` return except the CI-wait passthrough carries `auto_merge_eligible=False`; inside `wait_for_required_contexts`, `auto_merge_eligible=True` is returned by exactly one statement — the `complete` branch (`:305-306`) — which requires all 13 `REQUIRED_CONTEXTS` to be present with value `success` in a map built from a real `/check-runs` + `/status` read (`reported_contexts` is `None` in production). A renamed or absent context yields `None` from `statuses.get`, so the gate fails closed. `ci_result.mode is GITHUB` is reachable in exactly two ways, both sound: preflight already resolved `github` from completed Actions history, or `maybe_upgrade_ci_mode` upgraded after observing a *completed* required context (its `reported_contexts` are keys of the conclusion map, so a mere queued run cannot upgrade). Finally `enable_auto_merge` re-checks `config.auto_merge_enabled and ci_mode is GITHUB`. The upgrade and the approval result are mutually exclusive by construction — the upgrade branch requires `not awaiting_workflow_approval` and the approval branch returns `transitioned=False` (`:250-260`) — so no observation can both upgrade the mode and be reported as held. The one thing I cannot verify without a real API call is the *content* of `/check-runs` for the pinned Superset workflows, i.e. whether all 13 names ever appear simultaneously with `success`; if they do not, the failure mode is "never auto-merges", which is safe.

**Is `decide_resume` complete, and is `SKIP` on `converged` still safe?** The table is total: `persisted is None` is handled first, the three terminal-ish states short-circuit, `converged` requires artifacts, and the two `DEFER` rules are guarded by `not has_local_artifact`, so every remaining combination falls through to `RESUME`. I enumerated the lifecycle states against `{no artifact, local artifact, remote marker only}` and found no state × artifact pair reaching a wrong branch. `SKIP` on `converged` is safe now precisely because it is conditioned: a `converged` row with no artifact takes `RESUME` and publishes, which was the trap I flagged in iteration 4. The residual risk is not in the function but in its consumer (**M-1**).

**Crash immediately after each write, on the next run.** `dispatching` reservation, before any commit: `RESUME` → identical `prepared` (no duplicate row) → `create_branch` 422 with the branch still at `base_sha` → sessions re-run cleanly. **After the implementer's first commit, before the issue write: permanently deferred (M-1).** `issue_created`: `RESUME` → `existing_issue_number` suppresses the duplicate issue, `create_pr` runs, `after_ci` re-renders with the recorded number, `patch_issue` completes — clean, and this is the path the consolidation genuinely fixed. **`pr_created`: permanently deferred, PR identity erased from the state file (M-1).** `issue_patched` / `comment_created` / `terminal`: `SKIP`, one row, no remote call. Degraded path: the issue-only branch writes one terminal row and no remote artifact, so a crash before it simply re-renders; the PR-comment branch behaves like `pr_created` and inherits **M-1**. Marker search unavailable at any point: `DEFER` without a write, resumable next run.

**Row hygiene on the changed paths.** `DEFER` from `(persisted or candidate)` preserves recorded artifacts at both `_publish_live` sites (`:210-217`, `:592-603`) and at `_prepare_live_candidate:876-884` — but *not* at `_prepare_live_candidate:927-934`, which copies from the already-stripped `prepared` (**M-1**). The `terminal`-on-merge branch writes one row and cannot strand the issue patch: `patch_issue` and `after_issue_patched` both precede the auto-merge call inside `publish_artifacts` (`:703-718`), so `links.merged_at is not None` implies the patch already landed. Green happy path is still exactly one row per write, since the final row's `model_dump` equals the `issue_patched` row; the non-green path adds one enriching row; the label/CI mutations that *should* have made it differ are dropped (**m-1**).

**Is `pipeline_verified` sound in both directions?** Yes, with one observation. It cannot credit a PR we never observed green: `latest.reason is None` on an `issue_patched` row implies `ci_reason_holder[0]` was `None` at the time `after_issue_patched` ran, and with `wait_for_ci=True` that happens only on the all-green `complete` branch (the `wait_for_ci=False` mode belongs to the degraded path, which reaches `comment_created`, never `issue_patched`). Adding `pr_number` equality closes the "different PR on the same branch" case. In the other direction it cannot wrongly reject our own auto-merged PR: every field it requires is one the successful path sets. The stale `auto_merge_eligible: true` from **m-1** only makes the predicate more permissive, and it is dominated by the `reason is None` requirement, so it does not create a false verification.

**Is the self-consistency gate now enough (F6)?** For a first LIVE run on a scratch fork, yes, as a recorded caveat rather than as a proof. The two new checks remove the cases a *sloppy* role can produce — the empty diff and the no-commit branch — and §14's test-edit invariant is still enforced against the reported diff by the implementer/reviewer classifiers. What is left is a role that commits real work and misreports which files it touched; that is a dishonest-agent threat model, and the only real defence is comparing against `GET /pulls/{n}/files`, which is ~20 lines and one API call. I would ship without it only while `auto_merge_enabled=false`, because with auto-merge on it is the last gate between a misreported test edit and a merge.

**`_write` without retries.** Acceptable, and better than before: the retry that matters lives in the transport (`http_transport.py:120-149`, `429` and rate-limit-exhausted `403` with server timing), the deleted client layer had no producer, and exhaustion surfaces as `HttpTransportError` → per-candidate deferral with a durable row. The remaining exposure is GitHub's *secondary* rate limits on rapid writes, which return `403` with `retry-after` and are covered by the same transport branch.

## 5. Fit for a first LIVE run

**(1) Can anything left corrupt or orphan artifacts on the target?** Not on an uninterrupted run. Nothing can create a duplicate issue or PR: the reservation is `flock`-protected and marker-aware, a failed marker search now defers instead of writing, `existing_issue_number`/`existing_pr_number` suppress repeat writes, and `create_pr`'s 422 adopts the open PR. Nothing writes out of order. But **an interrupted run does orphan**: per **M-1**, a process death anywhere in the CI-wait window leaves an issue that is never patched with its PR link and a candidate that no subsequent run will ever complete, with the PR number erased from `state/candidates.jsonl`. Since a 90-minute CI wait per candidate is the norm here (**M-2**), that window is large in wall-clock terms. My recommendation: fix M-1 first — it is three small edits plus one assertion — or, if you want to run before fixing it, run with a single candidate, `ci_wait_timeout_s` in the low hundreds, and treat any interruption as requiring manual reconciliation of the issue/PR pair.

**(2) Can anything merge without observed green CI?** No. See the chain in §3: `enable_auto_merge` is reachable only through the single `complete` branch requiring all 13 required contexts to read `success` from a live API response, plus `mode is GITHUB` (preflight history or the observed upgrade), plus `config.auto_merge_enabled`, plus test evidence, plus the callee's own re-check. Nothing else in the repository calls it. Removing the preflight kill-switch did not weaken this; it moved the same requirement into the observation itself. The residual risk is not "merge without green CI" but "merge on a *misreported* diff that is green" — F6's remaining hole — which is why I would keep `auto_merge_enabled=false` for the first run regardless.

**(3) Caveats to record in §19 for a run starting at `ci_evidence_mode=local`:**

- The run-level recorded mode stays `local` even where a candidate's CI wait upgraded to `github` and auto-merged under it; there is no per-candidate mode field, and each candidate emits its own `mode_from=local` transition event (**m-2**). §19 should say the mode is recorded per run at preflight, and point at `ci_mode_transition` events in `events.jsonl` for the actual per-candidate evidence.
- A fork PR held by the first-time-contributor workflow gate is recorded as plain `ci_evidence_unavailable`, **not** `awaiting_workflow_approval` as §10.1 requires, and only after the full `ci_wait_timeout_s` elapses for that candidate (**M-2**). Either strike the distinction from §19 or note it as unimplemented.
- `merged_clean` and `merge_rate` will read 0 for a single run even where auto-merge succeeded; verified merges are credited by the *next* run's discovery path (**m-3**).
- A label-publication failure is recorded only as a PR comment, not as `artifact_degraded` on the row (**m-1**), so the KPI degradation count understates it.
- Convergence evidence rests on role-reported diffs plus the two new self-consistency checks, not on the branch's actual file list (**F6**); state that explicitly next to any claim that §14's "implementer commits non-test paths only" invariant held.
- The `red_baseline` observations remain reviewer-reported (iteration-2 M2', unchanged), so §19 should not claim the pipeline independently observed a red baseline.

## 7. Not assessed, and what a scratch-fork dry run would settle

Unassessed here: `tests/**` (in flux, and not evidence either way); the Devin session API beyond code reading; ACU accounting; the lane enumerators, `red_baseline` internals, gate/score modules and report renderers, none of which these two commits touch; the Docker image was not built.

What only a real API call can settle — my list for the dry run, in the order I would check them:

1. Whether all 13 `REQUIRED_CONTEXTS` names appear in `/commits/{sha}/check-runs` for a PR on the pinned fork, and with what timing. This decides whether `github` mode and auto-merge are reachable at all, and how long the wait really takes (**M-2**).
2. What the fork's held-workflow state actually looks like in `/check-runs` and `/status` — whether any required context appears with `status: waiting`/`queued` or `conclusion: action_required`, or nothing at all. This confirms or refutes M-2's core claim.
3. `merged_at` on `GET /pulls?state=all` list items and on `GET /pulls/{n}` immediately after enabling auto-merge — the basis of the merged/closed classification and of **m-3**.
4. `/search/issues` behaviour for a freshly created issue: indexing lag and whether the marker query matches PR bodies as well as issue bodies. Both feed the `DEFER` rules; a lag longer than the run means first-run candidates are dedupe-blind, and PR matching feeds M-1's guard.
5. `create_pr`'s and `create_branch`'s real 422 payloads, and `branch_sha` on a branch that our own previous run advanced — the exact input to **M-1**'s mismatch deferral.
6. Whether the generated PR title passes the vendored regex for each lane in practice (now a deferral rather than an abort, so a silent one).

I would run all six against a scratch fork with `auto_merge_enabled=false`, a single high-tier candidate, and a small `ci_wait_timeout_s`, and I would fix **M-1** before the run rather than after, because the run itself is the most likely source of the interruption that triggers it.
