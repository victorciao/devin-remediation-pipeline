## 2. Findings

### G1 — major — a failure after the PR write is still unrecoverable: the `pr_created` row loses the issue number, the new guard defers it, and the deferred row is then terminal forever

- File: `src/pipeline/__main__.py:207-223`, `:322-352`, with the permanence at `:148-150` and `:1042-1044`
- Plan: §7 mandated ordering (issue → PR → issue-patch); §14.1 lifecycle durability and "a re-run resumes durable state and completes the partial artifact set".
- Code: `after_pr_created`'s row is `candidate_for_callback.model_copy(...)` where `candidate_for_callback` is bound at `:322` to the candidate rebuilt at `:224-237` from the persisted row. On a first run that persisted row is the `dispatching` reservation, so `issue_number`/`issue_url` are `None`. The callback receives holders for the PR number, head SHA and CI reason but **not** `issue_number_holder`, so the `pr_created` row silently supersedes the `issue_created` row that did carry the number (last-write-wins, `state.py:90-103`). On the next run the candidate reaches `:207`: `persisted.issue_number is None and persisted.issue_url is None` is true, and `existing_artifact()` returns true because the latest row's state is `pr_created` — so the candidate is **deferred**, not resumed. That deferred row still carries `pr_url`, so `_prepare_live_candidate` returns it (`:1042`, `prepared.pr_url is not None`) and `_publish_live` discards it at `:148` on every subsequent run.
- Trigger: any exception or process death between `create_pr` and `patch_issue` — i.e. anywhere inside the CI wait, which is the longest step in the run (up to `ci_wait_timeout_s`, default 5400s): a 502 on the body PATCH, a malformed check-runs response, a `validate_pr_body` failure inside `after_ci`, an operator interrupt. Result: an issue that is never patched with its PR link, a PR that is never labelled or auto-merge-evaluated, and a candidate permanently frozen. The degraded path is worse: `issue_number` is `None` there by definition, so **no** degraded candidate whose PR exists is ever resumable. A third trigger needs no crash at all: `existing_artifact` falls through to `marker_exists`, and `/search/issues` indexes pull requests as well as issues, so a candidate whose PR body carries the marker can be deferred by the guard on a clean re-run.
- Fix: pass `issue_number_holder` into `after_pr_created` (and to the deferral copies) so the `pr_created` row records the issue; narrow the `:207` guard to the case it was meant for — a row with **no** artifact of any kind (`pr_url is None and issue_url is None`) — and exclude `pr_created` from the states that make `existing_artifact` true for the candidate's own row; and stop treating a `deferred` row as terminal at `:148`/`:1042` when it carries an incomplete artifact set (re-enter publication with the recorded PR).
- Note: this is the third iteration in which this crash window has been the headline finding. The mechanism is different each time, which suggests the resume rules should be expressed once, as a single function over `(persisted_state, artifacts_present)` returning `skip | resume_at_step | defer`, and asserted directly, rather than as three separate inline guards in the loop.

### G2 — major — the reviewed head is resolved once, so no LIVE candidate can converge after a rerun

## 3. Answers to the specific questions

**Is the self-consistency diff gate alone sufficient (F6)?** No. It closes the "reports files it did not commit" case and leaves the "reports nothing" case open: `committed_diff: ""` with `files_changed: []` is self-consistent, produces an empty `changed_paths`, satisfies `changed_paths <= read_paths` for any `files_read`, raises no finding, and can converge and satisfy the auto-merge conjunction — so §14's "implementer commits non-test paths only" still rests on the implementer's honesty. Two cheap steps make it sufficient without the full branch reconciliation: (a) reject an iteration whose implementer reports an empty `committed_diff` while claiming addressed criteria or a non-empty `commands_run` — a role that changed nothing cannot have implemented anything; (b) compare the resolved branch tip against the recorded `base_sha` (both already available via `branch_sha`) and reject convergence when the branch has no commits. Full `GET /pulls/{n}/files` reconciliation remains the right end state, and until it exists this hole must be recorded as a caveat on any run with `auto_merge_enabled=true`.

**Does short-circuiting on `converged` create a state where publication never happens?** Not on the paths I could reach. `_publish_live` is the only writer of `converged`/`terminal` rows, and the review loop's `converged` verdict lives on the in-memory candidate rather than in the state file — `run_once` appends no row between review and publication. So a `converged` row implies publication already happened. It is nonetheless a latent trap: any future code that persists the review verdict would silently disable publication for that candidate. The short-circuit should test artifact presence, not just state (see the consolidated resume predicate in **G1**).

**Rows per completed write, on every path.** Happy path with issues: `dispatching` (once, from `_prepare_live_candidate`), `issue_created`, `pr_created`, `issue_patched`, and the final append suppressed by the `model_dump` comparison — four rows, four writes. Non-green CI: the final row differs (it adds `auto_merge_eligible=False`) and is appended, so five rows for four writes, which is legitimate enrichment. Degraded: `dispatching`, `pr_created`, `comment_created`, plus a final `comment_created` that loses the degradation marker (**G6**). Resume with an existing PR: an extra `pr_created` row for a write that did not happen (**G6**). Issue-only: `issue_created` from the callback and then `published.append(state_store.resume(...))` with no second append (`:301`). Degraded issue-only: one `terminal` row, no remote write. The `model_dump` comparison cannot suppress a row that should exist, because the lifecycle `state` differs at every stage.

**Is a merged PR discovered on resume genuinely a success?** As a *terminal* state, yes — nothing more can be done to it, and deferring it (the old behaviour) was wrong. As a *clean automated merge* in §11, no: see **G5**.

**Can `after_ci` misbehave?** Raising: `validate_pr_body` throws `ValueError`, which the containment tuple catches — the PR exists, the issue is unpatched, and the candidate lands in the **G1** trap. Twice: idempotent. On a resumed PR: the issue number comes from `issue_number_holder`, seeded from the persisted row at `:268`, so the re-rendered body keeps `Closes #n` — provided the persisted row has the number, which is exactly what **G1** breaks.

**Auto-merge and SIMULATE containment, re-checked after the move.** Auto-merge is still impossible without an observation by construction: `ci_probe` is mandatory (`github_client.py:718-719`), `ci_result = ci_probe(pr_number)` is unconditional (`:733`), the conjunction still requires `ci_result.auto_merge_eligible and ci_result.reason is None` plus test evidence (`:749-758`), `wait_for_ci=False` returns a non-eligible result (`__main__.py:379-380`) and its only caller is the degraded path, which has no auto-merge call, and `enable_auto_merge` re-checks the config itself (`:665-673`). `wait_for_required_contexts` is unchanged and still requires literal `success` for all 13 contexts. SIMULATE containment is also intact after the move: `_publish_live` — now including the new degraded report write — is reachable only from the `Mode.LIVE` branch (`__main__.py:1207`), `live_client`/`head_sha_resolver` are `None` outside LIVE (`:1011`, `:1076-1079`), `_write` still raises `SimulationWriteError`, and `_read` still raises without a transport. My SIMULATE run made no network call and produced the full artifact set.

### Where I draw the line (iteration 4 of `iteration_cap = 5`)

**Must fix before LIVE:**

- **G1** — a transient error in the CI window silently abandons a candidate with an orphaned, unpatched issue, and no later run repairs it. It also makes degraded runs entirely non-resumable. This is the specific failure §14.1's durable state exists to prevent, and the fix is small (pass the issue number into `after_pr_created`; narrow the `:207` guard; stop treating a `deferred` row with artifacts as terminal). I would additionally consolidate the three resume guards into one predicate before the next attempt, because this defect has now survived three different fixes.
- **G2** — every LIVE candidate that needs a second iteration is predetermined to terminate unresolved after paying for the rerun's sessions. One-line fix (re-resolve inside `rerun`).

**Acceptable with a recorded caveat:**

- **G3** — provided the run's operating point is explicitly recorded as `ci_evidence_mode=local`, which hard-disables auto-merge and labels every candidate `needs-human-review`. That is a coherent, safe operating point; what is not acceptable is leaving §10.1 and §19's `test_ci_evidence_mode_upgrades_once` in the plan as though implemented. Pick one: implement the upgrade, or amend the plan and the evidence set. This is your call, not a code defect I can settle.
