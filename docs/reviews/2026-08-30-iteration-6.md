## 2. Findings

Severity ladder: `blocking` (a first LIVE run cannot succeed, or a safety invariant is bypassed) | `major` | `minor` | `nit`.

### B-1 — blocking — phase B is skipped precisely when the reviewer obeys its own output schema

- File: `src/pipeline/session_client.py:779-804` (the trigger), `:449-482` (the reviewer schema), `:714-746` (the validated predicate)
- Plan: §2 phase B ("the reviewer reads the implementer's full diff … a recorded phase-B diff review"), §9 step 4, §12.1 `diff_reviewed`
- Observed: the reviewer's `structured_output_schema` lists `diff_reviewed` in `required`, typed as an object with required `base_sha`, `head_sha`, `files_read`. A reviewer that conforms therefore returns a truthy `diff_reviewed` mapping from **phase A** — a phase that ran concurrently with the implementer and could not have seen its diff. `phase_b()` gates on `output(result.reviewer).get("diff_reviewed") not in (None, False)` and returns early. The message is never sent; `poll_session_after_message` is never called; `phase_b_attempted` stays empty. `iteration_from` then applies the real predicate (`:714-746`) — `files_read ⊇ implementer changed paths`, `base_sha == candidate.base_sha`, `head_sha == candidate.head_sha` — which a phase-A mapping cannot satisfy, so `diff_reviewed=False`. `run_review_loop` grants one incomplete rerun (`review_loop.py:203-226`); the rerun's fresh reviewer session is a new session id, so `phase_b()` evaluates the same condition on the same schema and skips again; the second incomplete attempt returns `TERMINAL / DIFF_REVIEW_INCOMPLETE`, `iterations = ordinal - 1 = 0`.
- Trigger: LIVE, every lane, every candidate, first iteration. Identical signature to the dry run (`iterations=0`, no publication) with a different proximate cause. In SIMULATE the whole function returns early at `:782-784`, which is why no SIMULATE run can surface it.
- Fix: gate phase B on the *validated* predicate, not the raw self-report — i.e. compute the `iteration_from` diff-review check first and send the phase-B message whenever it is `False` and phase B has not been attempted for this reviewer session. Concretely, extract `:714-746` into `validated_diff_review(result) -> bool` and use it in both places; then `phase_b()` becomes `if reviewer_session_id in phase_b_attempted or SIMULATE or validated_diff_review(result): return result`. Independently, remove `diff_reviewed` from the phase-A reviewer schema and add it only to the phase-B response contract, so a compliant reviewer cannot claim a diff review it structurally could not have performed.

### B-2 — blocking — nothing ever puts a commit on the candidate branch, so every candidate fails the "no commits beyond base" gate

- File: `src/pipeline/prompts.py:33-47` (`_preamble`), `:125-173` (implementer/reviewer/phase-B bodies), `src/pipeline/session_client.py:579-604` (the join), `:745-759` (the gate), `src/pipeline/__main__.py:857-954` (`_prepare_live_candidate`)
- Plan: §9.2 — "The orchestrator creates `devin/remediation/<candidate_id>` from the target base and pins `base_sha`; it — not the sessions — opens the PR, and only after JOIN" and "the implementer commits non-test paths only and **rebases onto the reviewer's commit at JOIN**"
- Observed: the orchestrator does create and pin the branch, and the prompts state its name. But no prompt instructs any role to *check out that branch*, to *push* to it, or to rebase at JOIN — `_preamble` tells each role to "clone the target repository and check out the base SHA if needed", and the implementer body says only "commit with `git commit --signoff`". Two sessions therefore commit on two private clones, on detached `base_sha`. The orchestrator never pushes either. `head_sha_resolver` reads `client.branch_sha(head_branch)` from GitHub (`__main__.py:1192-1199`), which is still `base_sha`, so `iteration_from` appends the blocking finding "candidate branch has no commits beyond base" (`:745-759`) on every iteration, and `expected_head` can never match any honest reviewer `head_sha`. Even with **B-1** fixed, convergence is impossible; and if a candidate somehow converged, `create_pr` would take the 422 path with "No commits between", where `pull_request_for_head` finds nothing and `GitHubResponseError` propagates into a `capability_unavailable` deferral.
- Trigger: LIVE, every lane, first iteration. Unreachable in SIMULATE, where `head_sha` comes from fixtures.
- Fix: state the branch contract in the prompts — check out `head_branch` (created from `base_sha`), commit only the role's own paths, `git push` the branch, and report the resulting `head_sha` in the structured output; give the implementer the explicit JOIN instruction to `git pull --rebase` onto the reviewer's test commit before its final push, and give the reviewer the reciprocal "do not force-push" instruction. Then verify server-side rather than trusting the report: after JOIN, require `branch_sha(head_branch) != base_sha` and that `commit_messages_between(base_sha, head)` contains both roles' signoffs before phase B is even sent, and turn "branch unchanged after both sessions finished" into an explicit `reason` distinct from `disagreement_unresolved` so the run report names the real cause.

### B-3 — blocking — reviewer findings are never fed back to the next iteration

- File: `src/pipeline/session_client.py:806-823` (`rerun`), `:584`/`:590` (the prompts it reuses), `src/pipeline/prompts.py:125-173` (no findings parameter exists)
- Plan: §2 step 3 / §9 step 5 — the implementer and reviewer iterate on the findings until no `blocking` or `major` finding remains, within `iteration_cap`
- Observed: `rerun` computes a new attempt ordinal and calls `concurrent_roles(next_attempt)`, which submits `resolved_implementer_prompt` and `resolved_reviewer_prompt` — the strings built once at `:605-628` from the planner output. No renderer in `prompts.py` accepts findings, the prior diff, or the prior iteration's failure, and `rerun` passes none. Iteration N+1 is therefore a statistically independent retry of iteration N, not a correction of it, while `attempt:<n>` tagging (`:225-259`) guarantees the API will not dedupe it — so the loop burns 2 sessions and up to 2×ACU per ordinal with no mechanism for the second attempt to be better than the first. It also silently violates §12's intent for retry ordinals: the ordinal exists to make a *distinct request*, and here the request is byte-identical apart from the tag.
- Trigger: LIVE, any lane, any candidate that does not converge on iteration 1 — i.e. every candidate that reaches the loop at all.
- Fix: add a `previous_iteration` argument to `render_implementer_prompt` / `render_reviewer_prompt` (findings with severity, criterion id, file/line, note; the reviewer's failing test and its output; the prior head SHA) and re-render inside `rerun` rather than reusing the captured strings. The renderers already have `_planner_text`; a `_findings_text` beside it is the whole change on the prompt side.

### M-1 — major — every session-error path discards the session evidence, so the run report can still show no trace of a real multi-session loop

- File: `src/pipeline/__main__.py:1264-1295` (the containment), `:1296-1310` (where ids are attached, after the `try`)
- Plan: §11 Layer 1 as the source of truth ("every candidate carries its role session ids"), §12.2
- Observed: `planner_session_id` / `implementer_session_id` / `reviewer_session_id` are attached to the candidate *only* on the success path at `:1296-1305`. In the `except` branch the row is rebuilt from `state_store.resume(...) or candidate` — a row written before any session existed — so a candidate whose planner, implementer and reviewer all ran and whose reviewer then timed out, hit a ceiling, or lost the transport is persisted as `deferred/capability_unavailable` with all three ids `null`, `iterations` unset, no `disagreement_summary`. `event_from_candidate` then emits an event with no session ids, `role_loop_events` (`observability/kpis.py:101-108`) excludes it from every session KPI, and the run report's escalation table (`observability/report.py:61`, `:105-140`) does not list it because its state is `deferred`, not `terminal`. That is exactly the reported dry-run symptom — "a run report that showed no trace of a three-session loop" — and the code can still produce it.
- Trigger: LIVE, any lane; concretely a reviewer `TimeoutError` from `poll_session_after_message` (`session_client.py:402-405`), a 5xx from the Devin API, or a `SessionCeilingError` mid-loop.
- Fix: have `run_candidate` attach whatever it already knows to the exception (or return a partial result) — the simplest form is a `SessionEvidence` payload on the exception types, carrying `planner/implementer/reviewer` ids, attempt ordinals and iteration count — and apply it in the `except` branch before appending the deferred row. Failing that, append a row per session creation (`dispatching` + ids) so the ids are durable before any failure can lose them.

### M-2 — major — a hard ceiling abort is contained per candidate and the run keeps spending

- File: `src/pipeline/__main__.py:1264-1273`, `src/pipeline/session_client.py:346-364` (`_record_terminal_usage`)
- Plan: §12.2 / §13 — `max_sessions` and `max_total_acu` are hard ceilings; hitting one aborts the run
- Observed: `SessionCeilingError` is in the per-candidate `except` tuple, so the candidate defers and the loop proceeds to the next candidate — which immediately re-triggers the same ceiling on its planner, defers, and so on for the whole remaining budget. Every one of those candidates is recorded as `capability_unavailable` rather than as a ceiling stop, and (with **M-3**) no event records the ceiling at all. The run then reports a report full of deferrals whose stated reason is wrong.
- Trigger: LIVE with `budget_N` > 1 once `max_sessions` or `max_total_acu` is reached, which the §13 defaults make reachable in a first real run.
- Fix: remove `SessionCeilingError` from the per-candidate tuple and let it reach `main`'s `RunAbort` handling (which already writes the report), or re-raise it as `RunAbort` after appending one `terminal/ceiling` row for the candidate in flight. Also record the ACU delta and the ceiling in an event via the existing `event_with_ceiling`.

### M-3 — major — the §12.2 retry and ceiling evidence helpers have no caller

- File: `src/pipeline/session_client.py:161-190`, `:850-851`; `src/pipeline/observability/events.py:60-134`
- Plan: §12.2 — the tri-state `is_new_session` check and its resolution must be recorded; §11 Layer 1

If per-attempt events are added, `read()`'s candidate/run split in `events.py` needs a third bucket so the KPI denominators do not double-count.

### M-4 — major — nested-marker lift validation is inert in LIVE because nothing ever populates `lifted_markers`

- File: `src/pipeline/session_client.py:700-705`, `src/pipeline/state.py:100-118` (`apply_red_baseline`, no caller), `src/pipeline/red_baseline.py:132-160` (`should_reauthor_baseline`, no caller), `:validate_nested_marker_lifts`
- Plan: §9.3 — a nested skip may be lifted only when the enclosing marker is accounted for; §14 fail-closed
- Observed: `inspect_reviewer_diff` is called with `lifted_markers=tuple(candidate.lifted_markers)`, and `Candidate.lifted_markers` is only ever set by `apply_red_baseline`, which the runtime never calls (`grep` finds the definition and the test only). `validate_nested_marker_lifts` consequently receives an empty lifted set and its `remaining_markers` default, so its parent-marker rule can never fire on a real reviewer diff. Until it is wired, treat "reviewer diff touches a marker and `lifted_markers` is empty" as a blocking finding so the gate fails closed rather than open.

### M-5 — major — a crash between `create_issue` and its state append strands the issue and defers the candidate forever

### M-6 — major — an adopted (reconciled 422) PR is never recorded, so the PR is permanently absent from state, events and KPIs

- File: `src/pipeline/github_client.py:709-745` (`created_pr` gating of `after_pr_created`), `src/pipeline/__main__.py:363-420` (`after_pr_created`), `:470-496` (`after_issue_patched`)

### M-7 — major — `verification_pass_rate` counts candidates that never verified anything as passing

### M-12 — major — the phase-B re-poll accepts a `blocked` session, and treats any output change as proof the message was processed

## 4. Areas I read and found sound

Recording these so the next round does not re-derive them: SIMULATE's no-write guarantee is structural at three independent layers, including the new phase-B path (see **m-6**). Ceilings are reserved *before* creation, not after — `_reserve` increments and rolls back on failure (`session_client.py:200-224`), and `max_acu_limit` is sent to the API so per-session cost is also enforced remotely; the only "after the fact" accounting is the total-ACU tally, which is inherent. `max_sessions >= budget_N * (3 + 2 * iteration_cap)` is validated at construction (`config.py:208-212`). Marker search fails closed: a failed or unconfigured lookup makes `marker_search_available` false, which forces DEFER and makes `append_if_new_artifact` refuse the reservation. Secrets: both transports read the credential from the environment per request, never store it on the object, never log it, and the sanitized `HttpTransportError` does not echo the auth header; the role prompts are rendered from candidate fields and planner output only — no config field carrying a token can reach them — and the Dockerfile bakes no credential and drops to an unprivileged user. Non-converged candidates cannot be published: every non-converged exit from `run_review_loop` sets `needs_human_review`, which becomes `Action.HUMAN_REVIEW`, which `_publish_live` filters out before any write. Role separation is enforced by construction (`RoleCollisionError`), and there is no third adjudicating role. Reviewer/implementer diff ownership, the empty-diff-with-claims gate, and the `files_changed` vs `committed_diff` cross-check are all real and strict. Drift matching cannot link co-located alerts (see **m-5** for the adoption bug, not the matcher).

## 5. Fit for a first real LIVE remediation run

**Not fit.** Concretely, against `victorciao/superset` at `a140e74f`:

- **(a) Can it converge a candidate? No.** Two independent blockers each guarantee `state=terminal reason=diff_review_incomplete iterations=0`, the same terminus as the dry run. **B-1**: phase B is skipped for any reviewer that conforms to the schema the pipeline itself supplies, because the trigger tests the reviewer's raw self-report while convergence tests a validated form. **B-2**: no role is told to work on, or push to, the prepared branch and no one performs the §9.2 JOIN rebase, so `branch_sha(head_branch) == base_sha` on every poll and the "no commits beyond base" blocking finding fires unconditionally. **B-3** means that even if a candidate got past both, the rerun could only repeat the failed attempt verbatim.
- **(b) Can it publish cross-linked issue and PR without orphaning or duplicating? Not reliably.** The ordering itself is right and duplication is well defended (marker search fail-closed, `append_if_new_artifact`, 422 reconciliation, `created_pr` gating). But two windows are not recoverable from durable state alone: a crash between the issue POST and its state append strands the issue and defers the candidate permanently with a false reason (**M-5**), and the reconciliation path never records the PR it adopted, so the PR survives on GitHub and disappears from the pipeline's state, events, links and merge KPIs (**M-6**). Both are "no duplicate, no completion" — safe, but not §14.1.
- **(c) Would it be honest about what it did and did not verify? No.** `verification_pass_rate` reports 100% for a run in which no diff was ever reviewed (**M-7**). "Dispatched Pr: N" still counts a state, not an artifact (**m-2**). The escalation table is dominated by candidates that never had a session, so the one candidate that burned three sessions is not distinguishable (**M-9**), and if that candidate failed on a session error its three session ids are dropped from the row entirely (**M-1**) — the dry run's second honesty defect, still reproducible. In `local` evidence mode, which is what this fork resolves to, the PR body is required by §10.1 to carry command output and carries none (**M-10**). A stale-skip candidate is counted as burn-down progress while shipping nothing (**M-8**).

Minimum set I would require before a first LIVE attempt: **B-1**, **B-2**, **B-3**, then **M-1**, **M-5**, **M-6**, **M-7**, **M-9**. **M-2**, **M-4**, **M-10**, **M-11**, **M-12** should land in the same round; the rest can follow.

## 6. Open questions only a real API call can settle

These are not findings; they are assumptions in the code (or in my reading of it) that no amount of source review can close. Each one is worth one cheap probe against a scratch session or a scratch fork before the first real run.

1. Does `POST /v1/sessions/{id}/message` resume a session already in `finished`, and does the resumed session re-emit `structured_output`, or does the follow-up answer arrive only as a message? `phase_b` depends on the former; `send_message`'s only failure detection is the substring `"not running"` in a `detail` field (`session_client.py:372-376`), which is a guess about the error shape.
2. Does the API enforce `structured_output_schema` strictly? If it does, **B-1** is certain (a compliant reviewer always emits `diff_reviewed`). If it merely hints, phase B is reachable for some fraction of reviewers, which is worse than either extreme — non-determinism in the convergence path.
3. Does a session that asks a clarifying question surface as `blocked` with a partially populated `structured_output`? That is the precondition for **M-12**'s false phase-B record.
4. Is `is_new_session` present in the creation response at all? `resolve_retry_decision`'s tri-state exists for the case where it is absent, but nothing has observed which case is real.
5. What are the actual check-run names on `victorciao/superset` for a PR from a branch of the fork itself, and does `head.repo.fork` read true for such a PR? `REQUIRED_CONTEXTS` completeness and **m-4** both depend on it.
6. How quickly does `/search/issues` index a newly created issue? The fail-closed dedupe assumes the marker is findable on the next run; a multi-minute index lag makes a fast retry duplicate-capable.
7. Is `PUT /pulls/{n}/auto-merge` even available on this fork (it requires the repository's auto-merge setting)? `enable_auto_merge` assumes a 200 and treats anything else as a transport failure.
8. Does the token's `security_events` scope actually return alerts for this fork, and does `code_scanning_alerts` come back paginated? The preflight reads one page.
