### B1' — blocking — the implementer production-only diff policy is unreachable, so §9.3/§14 has no runtime enforcement

- **File / lines**: `src/pipeline/session_client.py:366-374` and `528-559`
- **Plan clause**: §9.3 — "Any hunk touching an assertion, a fixture body, test logic, or a
  `@pytest.mark.skip` / `skipif` decorator → `needs-human-review`. This is enforced by a **diff
  classifier** in T10, not a filename check". §14 lists reviewer≠implementer ownership among the
  structural invariants; §12.1 fixes the role schemas.
- **Observed**: `iteration_from` calls `classify_implementer_diff` / `inspect_reviewer_diff` only
  when `implementer_payload.get("committed_diff", implementer_payload.get("diff"))` (resp. the
  reviewer's) is a `str`. The schema the pipeline actually sends
  (`ROLE_OUTPUT_SCHEMAS[SessionRole.IMPLEMENTER]`) requires `files_changed`,
  `criteria_addressed`, `commands_run` and describes no diff property at all; the reviewer schema
  likewise has no diff. No other caller of the classifiers exists in `src/` (`apply_red_baseline`
  and `should_reauthor_baseline` are also uncalled). The classifiers are therefore dead on every
  real path, and the code reads as if the invariant were enforced.
- **Trigger**: any LIVE candidate. The implementer session edits `tests/test_x.py` and removes a
  `@pytest.mark.skip`; its structured output reports `files_changed: ["superset/…", "tests/…"]`
  and no diff. `iteration_from` adds no finding; if the reviewer converges and CI is green and
  `risk <= 2`, `enable_auto_merge` fires on a PR that rewrote tests.
- **Fix**: add `committed_diff` (or `diff_stat` + per-file hunks) to both role schemas as a
  required property, and fail closed — treat a converged iteration whose implementer payload
  carries no diff as an incomplete iteration (as §12.1 already does for `diff_reviewed`) rather
  than as a pass. `files_changed` alone would let the path-based check run, which §9.3 explicitly
  rejects as insufficient.

### M1' — major — the `pr_created` row is written last, so any failure after `create_pr` diverges state from GitHub and the re-run cannot recover

- **File / lines**: `src/pipeline/__main__.py:262-341`; `src/pipeline/github_client.py:590-621`
- **Plan clause**: §14 "Idempotency/dedupe: re-runs must not open duplicate PRs/issues"; §14.1
  lifecycle (`issue_created` → `pr_created` → `issue_patched`); §10.1 the CI wait is up to
  `ci_wait_timeout_s` (default 5400 s).
- **Observed**: `publish_artifacts` creates the PR, then calls `after_pr` (which polls CI for up
  to 90 minutes), then `patch_issue`, then possibly `enable_auto_merge`; `_publish_live` then adds
  labels (twice, if a CI reason exists) and only at `:341` appends the `pr_created` row. Nothing
  persists the PR number/URL in between. Any exception in that window — a 5xx or rate-limit
  exhaustion inside `_required_context_statuses`, a `PreflightError` from `_mapping` on a
  malformed check-runs body, a label write denied because `needs-human-review` does not exist on
  the target (see **m11**), a crash or SIGTERM during the CI wait — propagates to `main`, aborts
  the run, and leaves state at `issue_created`. On re-run, `resume` finds no `pr_url`, skips issue
  creation correctly, and calls `create_pr` again for the same head branch; GitHub rejects it
  (a PR already exists for that head), `HttpTransportError` is not tolerated the way the branch
  422 is, and the candidate can never converge. The `issue_patched` state is never written at all
  (**m6**), so no row distinguishes "patched" from "PR created".
- **Trigger**: kill the process during the CI wait of a candidate whose issue and PR were created,
  then re-run with the same `--output-dir`.
- **Fix**: append the `pr_created` row immediately after `create_pr` returns (from inside a
  mandatory `after_pr`-style seam, before any CI wait), append `issue_patched` after
  `patch_issue`, and treat a "pull request already exists" 422 on `create_pr` as a resume by
  reading the existing PR for that head — symmetrically with `create_branch`'s 422 handling.

### M2' — major — the marker search query is double-encoded, so cross-run artifact dedupe never matches

- **File / lines**: `src/pipeline/__main__.py:123-127`; `src/pipeline/http_transport.py:104-107`
- **Plan clause**: §14.1 / §14 — the stable `<!-- devin-remediation-id: … -->` marker is the
  cross-run dedupe key searched before a first artifact write; re-runs must not duplicate
  artifacts.
- **Observed**: `search_marker` percent-encodes the whole query with `quote(...)` and then passes
  `"/search/issues?q=" + encoded` to the transport, whose `_request` encodes the path again with
  `quote(path, safe='/?:=&')`. `%` is not in `safe`, so `%3A` becomes `%253A`. GitHub receives a
  free-text query for the literal string `repo%3Ao/r%20%3C%21--%20devin-remediation-id%3A…`,
  which matches nothing (verified by reproducing the two-stage encoding locally). `marker_exists`
  therefore always returns `False`, and `existing_artifact` degrades to the local JSONL only.
- **Trigger**: any LIVE re-run against a target that already carries the marker while
  `state/candidates.jsonl` is absent (fresh `--output-dir`, or the poisoned-state case in **m1**):
  the pipeline re-creates issue and PR for a candidate that already has both.
- **Fix**: build the search path with `urlencode({"q": f"repo:{owner}/{repo} \"{marker}\""})` and
  let the transport do the only encoding (or pass query parameters through the transport
  unencoded). Add a test that asserts the exact request path reaching the transport.

### M3' — major — a degraded-sink run aborts entirely on the first medium-tier candidate

- **File / lines**: `src/pipeline/__main__.py:733-738` (and the same check at `153-156`)
- **Plan clause**: §14 label/artifact degradation — a degraded capability "falls back to a PR
  comment plus a `reports/` record rather than failing the API call"; §13 `issue_sink=pr_comment`
  "tags the run `artifact_degraded`"; §10.1/§3-0d require the run to reach publication and
  reporting.
- **Observed**: when `has_issues` is `False`, `run_once` raises
  `RunAbort("issues are disabled; issue-only candidates require issue_sink=pr_comment")` if any
  dispatched candidate has `action = OPEN_ISSUE` — regardless of `issue_sink`. But
  `run_live_preflight` already refuses to run unless `issue_sink is PR_COMMENT` when
  `has_issues` is `False`, so the message's own remedy is already in force and the abort is
  unconditional. Since `dispatch_candidates` maps every medium tier to `OPEN_ISSUE`

- **Fix**: route issue-only candidates in degraded mode to a `reports/` record (they already get
  one in `simulate_run`) plus `artifact_degraded` on the row, and continue the run; keep the hard
  abort only for a genuinely unsatisfiable configuration (`has_issues=False` **and**
  `issue_sink=issues`).

### M4' — major — the DCO trailer assertion can never observe a trailer

- **File / lines**: `src/pipeline/__main__.py:81-93` and `:116`; `src/pipeline/templates/render.py:63-70`, `113-115`
- **Plan clause**: §10 DCO — "The pipeline still signs every commit (`git commit --signoff`) and
  **asserts the trailer itself**"; §19 acceptance names "`Signed-off-by` trailer present".
- **Observed**: `_commit_message(repo_path, head_branch)` runs `git show -s --format=%B` in the
  **local** target checkout against the **prefix** `head_branch` (e.g. `devin/remediation`), not
  the per-candidate branch `{prefix}/{candidate_id}` — and the implementer's commits exist only
  on the remote candidate branch, never in the local checkout. The subprocess failure is
  swallowed (`return None`), `_commit_signoff(None)` returns `None`, `render_pr_body` silently
  omits the trailer section, and `validate_pr_body` does not require it. There is no other
  signoff check in `src/`, and no role schema field carries the trailer the implementer prompt
  asks it to report.
- **Trigger**: every LIVE PR.
- **Fix**: read the trailer from the artifact the pipeline actually has: either
  `GET /repos/{o}/{r}/commits/{head_sha}` after `after_pr` resolves `head_sha`, or a required
  `signoff_trailer` field on the implementer schema; then fail closed (`needs-human-review`) when
  it is absent, instead of rendering a PR body that quietly asserts nothing.

### M5' — major — `create_branch` 422 is treated as resume without verifying the existing ref's SHA

- **File / lines**: `src/pipeline/__main__.py:568-573`
- **Plan clause**: §9.2 — the reviewer's red baseline is taken at `base_sha` and the candidate
  branch is created from the pinned target base SHA; §14.1 records `base_sha` per candidate.
- **Observed**: any `HttpTransportError` with `status_code == 422` is swallowed — not just
  "Reference already exists", and with no check that the existing ref points at
  `prepared.base_sha`. A branch left by an abandoned earlier run (or by a human) at a different
  commit is silently reused: the state row and the session prompts claim
  `based on {base_sha}` while the branch head is something else, so the reviewer's "baseline at
  `base_sha`" and the PR's diff are computed against a base the pipeline never observed. 422 is
  also GitHub's generic validation status (e.g. an invalid ref name), so a real failure is
  swallowed too and publication later fails with a confusing "candidate branch was not prepared".
- **Trigger**: run, kill it after `_prepare_live_candidate`, let the target base branch advance,
  re-run without a state file (or with a row whose `base_sha` was re-resolved) — the stale branch
  is adopted.
- **Fix**: on 422, `GET /git/ref/heads/{branch}`; if the SHA equals the recorded `base_sha`,
  resume; if it differs and no PR exists for the branch, either fast-forward/reset the ref or
  defer the candidate with an explicit reason. Re-raise 422s whose body is not
  "Reference already exists".

### M6' — major — only `SessionCeilingError` defers a candidate; every other session failure aborts the whole run

- **File / lines**: `src/pipeline/__main__.py:796-816`; `src/pipeline/session_client.py:268-271`, `282-332`
- **Plan clause**: §13 `max_sessions` row — a ceiling reached mid-run "defers the *current
  candidate* … and the run continues to publication and reporting (§12, §14.1)"; §12.2
  `session_timeout_s` per role; §14.1 requires re-runs to resume from durable state.
- **Observed**: the `try` around `orchestrator.run_candidate` catches `SessionCeilingError` only.
  `TimeoutError` from `poll_session` (a subclass of `OSError`, so `main` catches it and exits 1),
  `SessionDedupeError`, `RoleCollisionError` and any `HttpTransportError` from the Devin transport
  propagate out of the per-candidate loop: the run ends with no publication for candidates whose
  sessions already finished, and the ACU already spent on them is lost with no state row. A role
  session timing out is the single most likely runtime failure (`session_timeout_s` default
  5400 s per role). Related: `_reserve` increments the counter before creation, so a failed
  creation still consumes a session slot, and when a ceiling is hit inside the
  `ThreadPoolExecutor` join the sibling role session has already been created and is abandoned
  un-cancelled.
- **Trigger**: one reviewer session that never reaches a terminal status; every other candidate in
  the run loses its publication.
- **Fix**: catch the per-candidate failure classes (`TimeoutError`, `SessionDedupeError`,
  `RoleCollisionError`, transport errors) alongside `SessionCeilingError`, append the deferral row
  with the matching reason code, and continue; keep `RoleCollisionError` fatal only if the
  collision is configuration-wide rather than candidate-scoped.

### m8 — minor — `wait_for_required_contexts` spins on injected contexts and burns the full timeout on `neutral`/`skipped`

- **File / lines**: `src/pipeline/github_client.py:326-361`
- **Plan clause**: §10.1 — `github` mode waits at most `ci_wait_timeout_s`; on expiry the
  candidate is `ci_evidence_unavailable`.
- **Observed**: deadline arithmetic is correct (`ci_wait_timeout_s - elapsed_s`, clamped at 0, so
  a caller that has already consumed the budget exits after one probe) and both `clock` and
  `sleep` are injectable. But when `reported_contexts` is supplied and `poll` is left at its
  default `True`, the loop re-evaluates the same immutable mapping until the deadline, sleeping
  `poll_interval_s` each time — a caller-visible foot-gun with no possible state change. A
  required context that concludes `neutral` or `skipped` (or is permanently absent, e.g. renamed
  upstream) never satisfies `success` and never matches the failure set, so the candidate consumes
  the entire 5400 s before downgrading. Note also that once every context has reported `success`
  the function returns immediately, so a `failure` re-reported afterwards on the same SHA is not
  observable — acceptable, since GitHub's own auto-merge re-evaluates required checks, but worth
  recording.
- **Fix**: treat `reported_contexts is not None` as implying a single evaluation, and classify
  terminal-but-not-success conclusions (`neutral`, `skipped`, `action_required`, `stale`) as an
  immediate non-green outcome instead of waiting for them to change.

### m9 — minor — the merge-rate KPI reports convergence, not merges

- **File / lines**: `src/pipeline/observability/kpis.py:100-107`, `165-169`
- **Plan clause**: §11 — "PR merge rate (merged-clean vs edited vs rejected)" with the
  `merge_rate_floor = 0.50` alert.
- **Observed**: `_merge_rate` counts events whose `terminal_outcome is CONVERGED` as merged; the
  pipeline never reads the PR's merge state from GitHub, so an open (or closed-unmerged) PR that
  converged locally counts as merged, `edited` is a residual (`total − merged_clean − rejected`),
  and the alert is effectively unreachable. `merged_clean` additionally leans on
  `test_exempt_reason`, which is never populated (**M7'**).
- **Fix**: record `merged`/`merged_at` per candidate from `GET /pulls/{n}` (or the auto-merge
  callback) and compute the rate from that; otherwise rename the metric to `convergence_rate`.

### m10 — minor — `publish_artifacts` accepts a caller-asserted `ci_green`

- **File / lines**: `src/pipeline/github_client.py:562-621`
- **Plan clause**: §14 — no auto-merge without the full CI gate stack green.
- **Observed**: `ci_green` is a plain parameter; `after_pr` overwrites it only when supplied.
  `publish_artifacts(..., ci_green=True)` with `after_pr=None` reaches `enable_auto_merge` with no
  observation whatsoever. The current live caller always passes `False`, so this is latent, but
  the safety property now rests on caller discipline at a public seam — the same shape as the
  iteration-1 B1 defect. The module functions also reach into `client._config`, so the guard and
  the state it guards are not co-located.
- **Fix**: drop the `ci_green` parameter and require a `ci_probe: Callable[[int], CiWaitResult]`;
  when it is absent, auto-merge is impossible by construction.

### m11 — minor — the §14 label preflight and its denial fallback are missing

- **File / lines**: `src/pipeline/github_client.py:543-549`; `src/pipeline/__main__.py:321-325`
- **Plan clause**: §14 Label preflight — "`needs-human-review` does not exist on the target.
  Dispatch ensures it once (`GET` then `POST /repos/{o}/{r}/labels`); if creation is denied it
  falls back to a PR comment plus a `reports/` record rather than failing the API call."
- **Observed**: there is no label GET/POST anywhere in `src/`. Labels are passed straight into
  `create_issue` and `add_labels`, and any failure propagates as an `HttpTransportError` —
  aborting the run at a point where the state row has not yet been written (**M1'**). `add_labels`
  is also called twice when a CI reason exists (`:321` then `:325`), the second call re-sending
  the first call's labels.
- **Fix**: add `ensure_label` (GET, then POST once per run) with the plan's comment/`reports/`
  fallback on denial, and collapse the two `add_labels` calls into one.

### m12 — minor — `_changed_hunks` folds context lines into the classified content

- **File / lines**: `src/pipeline/red_baseline.py:156-200`
- **Plan clause**: §9.3 — the classifier judges *hunks that touch* assertions, fixtures, test
  logic or skip markers.
- **Observed**: `_changed_hunks` appends unchanged context lines (those starting with a space)
  alongside `+`/`-` lines, and `classify_implementer_diff` then scans that mixed set for
  `assert` / `pytest.raises` / skip markers. A production-only hunk whose three lines of context
  happen to contain `assert` is rejected as an implementer test edit. Removed (`-`) lines are also
  treated identically to added ones. Currently masked by **B1'** (the classifier never runs).
- **Fix**: classify added and removed lines separately from context, and keep context only for
  locating the hunk.

### n1 — nit — dead enforcement helpers, one of which would re-widen CI evidence if wired

## 4. Areas read and found sound

- **Auto-merge conjunction (B1).** Traced above; `REQUIRED_CONTEXTS` is byte-identical to the §10
  13-context list, `License Check` is correctly excluded, and every non-`success` conclusion
  (including absent and renamed contexts) fails closed to `local` + `ci_evidence_unavailable`.
  `enable_auto_merge` also re-checks `auto_merge_enabled` and `ci_evidence_mode` itself.
- **`publish_artifacts` write order.** Issue → PR → issue patch holds for every early return:
  the `has_issues` guard raises before any write; the medium-tier / missing-PR-argument return
  happens after the issue and before any PR; `after_issue` fires only for a newly created issue,
  so a resumed issue is not re-recorded; `after_pr` cannot skip the patch (its return value only
  feeds the auto-merge conjunction); `publish_degraded` is PR → comment with no issue and no
  auto-merge. Both functions are single-candidate and stateless apart from the client.
- **Candidate identity and drift (LANE 1).** `candidate_id = sha256(lane|repo|stable_locator)`
  with `position_digest` over `start_line:start_column-end_line:end_column`; the four co-located
  `py/overly-large-range` alerts on line 55 (columns 6/9/12/15) yield four distinct digests and
  are excluded from weak-key drift matching by the multiplicity-1 requirement on both sides.
  `run_once` now feeds `current_scan` the full pre-normalization enumeration, which is the correct
  multiplicity universe; `supersede` writes both immutable rows.
- **Dispatch and containment.** Tier mapping, `budget_N` overflow deferral, containment-depth
  ordering, blocked/suppressed child routing with `related_candidate_id`, and the refusal to
  auto-merge at `risk >= 3` or with `unresolved_major` all match §6/§9.2. `_gated_out` raises on
  an unrouted reason rather than defaulting, which is the right failure mode.
- **`config.py` safety surface.** Derived `max_sessions` floor with a startup `ConfigError`
  (§13), `BUDGET_HARD_MAX` clamp behind `--i-know-what-im-doing`, `kpi_sink=gsheet` +
  `mode=simulate` rejected, `ci_evidence_mode=local` forcing `auto_merge_enabled=False` on
  construction and on assignment, `SecretStr` credentials, and LIVE requiring both credentials.
  (`model_copy` bypasses validators, but both in-tree copies set `auto_merge_enabled` explicitly.)
- **SIMULATE containment is structural for writes.** `GitHubClient._write` raises
  `SimulationWriteError` before touching a transport, and every mutating method routes through it;
  `run_once` constructs no GitHub or Devin transport outside `Mode.LIVE`; `SessionClient`
  short-circuits creation and polling before the transport reference in SIMULATE; `_publish_live`
  is called only under `Mode.LIVE`; SIMULATE forces `ci_evidence_mode=local` and
  `auto_merge_enabled=False` at the top of `run_once`. `simulation_fixtures.simulation_result`
  substitutes role output *after* the synthetic sessions run and is guarded by
  `mode is Mode.SIMULATE and candidate is not None` — a mode check, not a transport boundary, so
  the containment of *role output* is conventional even though the containment of *writes* is
  structural; a future caller that drops the mode check would inject fixtures into a LIVE run. The
  fixture deliberately exercises all three baseline classifications (`sha256(candidate_id)[0] % 3`),
  which is a good adversarial choice.
- **Secret handling.** Credentials live only in `SecretStr` config and in
  `os.environ` reads at call time; `_JsonHttpTransport` puts the token in a request header,
  raises sanitized `HttpTransportError` messages, and uses `raise … from None` so no urllib
  context escapes. No token value reaches a log, a rendered artifact, an exception message or a
  committed file on any path I read. `token_login`/`token_scopes` are identity metadata (not
  credentials) and are now written once per run to `reports/events.jsonl` rather than onto every
  candidate event, which is the right shape; they are not rendered into issue or PR bodies.
  `classify_red_baseline` truncates reviewer-supplied failure messages to 160 characters in its
  log line.
- **Template and title validation at the publication boundary.** `_publish_live` validates the
  issue body (or degraded comment body), the PR body, and the PR title against the vendored regex
  before any write, and aborts rather than publishing a non-conforming artifact. Security-lane
  issue bodies are rendered from the fixed `generic_tracking` shape (summary, module-only scope,
  status, verification, rule id) with no exploit detail, and `SECURITY_ISSUE_MODE` is asserted at
  render time.
- **Review loop convergence rules.** Unmapped reviewer criteria and unaddressed planner criteria
  become `major` findings; an unknown severity string parses to `BLOCKING` (fail-closed); an
  incomplete `diff_reviewed` iteration does not count toward `iteration_cap`; `stale_skip` is a
  distinct reviewer-only terminal outcome; there is no third adjudicator anywhere —
  `disagreement_unresolved` always routes to `HUMAN_REVIEW` with a rendered handoff summary. The
  loop cannot exceed `iteration_cap` and has no path that returns `converged=True` while a
  blocking or major finding stands.
- **Role separation and retry tri-state.** `resolve_retry_decision` implements §12.2 exactly
  (attempt 1 or `true` → proceed; `false` → fatal; `null` → compare with the previous attempt's
  id); `_issued_roles` rejects a session id issued to two roles under the lock; every creation
  sends `idempotent: true`, the `attempt:<n>` tag and the `attempt:` prompt preamble; per-role
  `max_acu_limit` is sent to the API and re-checked on completion, and the per-run ACU total is
  accumulated under the lock. The `ThreadPoolExecutor` join runs exactly two roles and shares no
  mutable state beyond the client's locked counters (`_previous` is written outside the lock but
  only ever under distinct `(candidate_id, role)` keys — worth tidying, not a defect I can trigger).
- **Enumerators.** LANE 2's AST walk tracks nested class/function scope, unconditional vs
  conditional markers, parametrization and `enclosing_skip_nodeid`; LANE 3's EOL arithmetic and
  caller/override counting behave as specified; both now surface unreadable/unparsable files as
  `failures` that `run_once` turns into capability notes (iteration-1 m5 closed).
