### B8-1 — blocking — the phase-B "no message history" fallback accepts an answer the session never gave

- File: `src/pipeline/session_client.py:561-570` (introduced by `7027edb`), in context `:532-600`; correlation helper `:287-305`.
- Plan: §12.2 (`docs/IMPLEMENTATION_PLAN.md:701-704`) — "**A follow-up answer is correlated, not inferred.** Phase-B output is accepted only once the session's `messages` array carries a `devin_message` whose `timestamp` postdates the `user_message` that delivered the phase-B request … A changed `structured_output` is not by itself evidence that this message was answered." P-3 records that every message carries `event_id` + `timestamp`, so correlation is always available on a well-formed response.
- Observed: `_message_processed` implements exactly the plan clause. The new branch then bypasses it: when `messages` is absent, non-sequence or empty, any `structured_output` that (a) differs from the pre-message snapshot and (b) contains a mapping under `diff_reviewed` is accepted as the answer to the phase-B message. The condition it replaces — "we cannot correlate" — is the one case where the plan requires refusal. Note that `_message_processed` already returns `False` for exactly these responses, so the branch exists solely to convert non-correlation into acceptance.
- Trigger: LIVE, every candidate whose reviewer session returns a `GET /v1/sessions/{id}` payload without a usable `messages` array — a truncated or paginated response, a field the API omits for long sessions, or any transport that returns the session object without its transcript. The structured output that satisfies it need not be an answer at all: `structured_output` merges keys across messages (P-2), the reviewer session is a live agent that continues to write output after phase A, and `changed_output` is only compared against the snapshot taken *before* the message was sent. A reviewer that emits a `diff_reviewed` object of its own accord (it has the branch, the base SHA and the diff from phase A) satisfies both clauses, and the pipeline then converges a candidate on a review it never requested and never correlated. The same path also silences the honest failure mode: a session that answers in prose is supposed to time out, not be accepted.
- Fix: delete the branch. If `messages` is missing, keep polling and let `session_timeout_s` expire, recording a distinct reason (e.g. `phase_b_correlation_unavailable`) so the candidate defers with a true cause instead of converging. If the intent was to tolerate a transport that genuinely never returns `messages`, prove that from the API first and then correlate on a monotonic session field (`updated_at`) rather than on the content of the output being validated.

### B8-2 — blocking — `append_if_new_artifact` no longer bars a second writer, and the "absence" it trusts was proven before three role sessions ran

- File: `src/pipeline/state.py:276-292` (the reservation), `:136` and `:205-232` (the per-instance marker cache), `:55-59` (`has_local_artifact`); callers `src/pipeline/__main__.py:216-248`, `:930-1000`.
- Plan: §14.1 (`:868-872`) — "**Before any write** the pipeline re-reads state **and** searches the target repo for the marker"; §14 idempotency ("re-runs must not open duplicate PRs/issues"); §13 fail-closed.
- Observed, two mechanisms in one function:
  1. **The reservation reserves nothing.** `ae0837d`/`M7-3` made `has_local_artifact` require a real link (`state.py:57-59`), but the row this function writes is the `DISPATCHING` reservation, which by construction has no link. Under the lock the only tests are `has_local_artifact(current)` and the cached `marker_exists`, so a second process (or a second run of the same candidate) that arrives while the first is between `append_if_new_artifact` and `create_issue` sees no link and no marker, takes the lock in turn, appends its own reservation, returns `True`, and creates a second issue. The lock now serialises two writers rather than excluding one.
  2. **The proof of absence is stale.** `marker_artifact` memoises per `candidate_id` for the lifetime of the store (`:207-208`), and the store lives for the whole run. The search that establishes `ABSENT` happens in `_prepare_live_candidate`, i.e. *before* the planner, implementer and reviewer sessions (each up to `session_timeout_s`) and before publication. At the write, `resume_decision` (`:188-203`) and `append_if_new_artifact` (`:279`) both consult the cache, so the pipeline never re-reads the target repo before the write the plan says it must precede. Anything created in that window — a human filing the issue, a concurrent run, or the GitHub search index finally catching up on an issue this pipeline itself created and crashed before recording — is invisible, and the pipeline opens a duplicate on a real repository.
- Trigger: LIVE. (2) needs only ordinary latency between preparation and publication; (1) needs a second run or a retry of the same `candidate_id` while the first is mid-publication, which §14.1 names as the expected recovery workflow.
- Fix: (a) invalidate the cached outcome for the candidate immediately before the pre-write check (`self._marker_results.pop(candidate_id, None)`) so the search is re-taken inside the reservation, and fail closed if that re-take is `FAILED`/`ORPHANED`; (b) make the reservation itself exclusive — treat an existing `DISPATCHING` row for the candidate as a live claim (with a lease timestamp and TTL) and return `False`, rather than deciding on links alone; (c) keep the ABSENT proof and the write in one critical section so no session lifetime can elapse between them.
