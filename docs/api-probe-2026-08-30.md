# Devin sessions API probe — settled behavior for §12.1/§12.2

Recorded 2026-08-30 against `api.devin.ai` with a throwaway session
(`max_acu_limit: 2`, prompt: emit structured output and stop, no repository work). This file
exists because iteration 7 §4 listed four questions as answerable only by a real API call, and
the answers decide the phase-B design. Every line below is an observed response, not an
inference.

## P-1 A role session that finishes its work terminates at `status_enum: "blocked"`

The probe session emitted its structured output, replied with a `devin_message`, and settled at:

```
status:      "running"
status_enum: "blocked"
structured_output: {"phase_a_answer": "alpha"}
```

It never reached `finished`. A session that stops and waits for its caller is `blocked`; that is
the normal terminal shape for a role session, observed on both the initial run and after a
follow-up message.

Consequence for the code: polling that returns only on `finished` and raises on `blocked` fails
every successful role session. The terminal condition must be *`finished`, or `blocked` whose
`structured_output` already satisfies the role's required keys*. A `blocked` snapshot without
that output is a genuine block (the session is asking a question it cannot answer) and stays
fail-closed. `expired` remains a failure unconditionally.

## P-2 Structured output is not fenced by the creation schema, and is merged across messages

The session was created with a schema declaring only `phase_a_answer`. A follow-up message asked
for a `diff_reviewed` object; the resulting `structured_output` was:

```json
{"phase_a_answer": "alpha",
 "diff_reviewed": {"base_sha": "aaa", "head_sha": "bbb", "files_read": ["x.py"]}}
```

So a key absent from the creation schema does appear, and prior keys survive — output is merged,
not replaced. Phase B therefore does not need its creation schema re-scoped: the contract can be
stated in the phase-B prompt and enforced by parsing what comes back.

`POST /v1/session/{id}/message` accepts a `structured_output_schema` field with `200` and a
`null` body, but nothing in the response proves it was applied, so it must not be relied on as
enforcement. `POST /v1/sessions/{id}/message` (the plural spelling the code uses) also returns
`200`.

## P-3 Messages carry per-message identity, so a phase-B answer can be correlated

`GET /v1/session/{id}` returns `updated_at` and a `messages` array whose entries carry `type`
(`initial_user_message` / `user_message` / `devin_message`), `event_id` and `timestamp`:

```json
{"type": "user_message",  "event_id": "event-01a053fcb64a…", "timestamp": "2026-08-30T18:44:25.802185+00:00"}
{"type": "devin_message", "event_id": "event-01a053fcdca1…", "timestamp": "2026-08-30T18:44:4…"}
```

"This output answers this message" is therefore provable: accept phase-B output only once a
`devin_message` postdates the `user_message` that carried the phase-B request. Inferring
completion from a changed `structured_output` alone is unnecessary.

Timing note: `structured_output` was already populated while `status_enum` was still `working`,
so the output-present test must not by itself be read as terminal.

## P-4 A zero-match marker search is a `200`, not an error

```
GET /search/issues?q=repo:victorciao/superset "<!-- devin-remediation-id: … -->"
200 {"total_count": 0, "incomplete_results": false, "items": [], "search_type": "lexical"}
```

Absent is a successful `200` with `total_count: 0`; failures arrive as HTTP errors from the
transport. The three outcomes are distinguishable at the source, so a zero result must classify
as ABSENT (the precondition for a first write) and only a raised transport error as FAILED.

`GET /repos/victorciao/superset/actions/runs` → `total_count: 1`, the single run being event
`dynamic` (`CodeQL Setup`). No `pull_request` run has ever completed, so §10.1 resolves `local`,
auto-merge stays hard-disabled, and the local-evidence PR body validation is the path that
applies on the first LIVE run.
